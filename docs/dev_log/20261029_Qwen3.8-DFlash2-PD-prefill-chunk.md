# Qwen3.8 DFlash2：chunked prefill 切分规则与 P/D 分离验证（v0.31）

## 1. 背景及分析

Qwen3.8-27B-FP8 + DFlash2，`max_num_batched_tokens=6144`，8192 输入时的
chunk 由 5376/2688/128 变成了 6144/2048。本文记录原因、chunk 的计算规则，
以及 P/D 分离下 "P 不开投机" 的可行性验证。

### 结论一：chunk 切分由两层规则决定，项目更新没有改变调度

对 20261021 之前的代码（vllm `0670c36056` + 插件 `3a8c736`）与当前代码做了对照，
chunk 切分一致。10-21 以来 vLLM 的调度器与投机配置代码没有改动。

有效 chunk = `floor((N - draft_slots) / B) * B`，其中：

- `N` = `max_num_batched_tokens`。
- `draft_slots` = DFlash 的 `num_speculative_tokens`（这里是 5）。
  `scheduler.py` 把每个 chunk 限制在 `input_budget - draft_slots`。
- `B` = **实际** block size。混合模型会把 `--block-size` 抬到
  "attention 页 ≥ mamba 页" 的整数倍（`platforms/interface.py`
  `Setting attention block size to ...`）。本模型：不指定 → 832，128 → 896，
  256 → 1024。
- 开 prefix caching 时 mamba 进入 `align` 模式，chunk 末尾必须落在 block 边界；
  投机解码默认 `use_eagle_block_drop`，最后一个可缓存位置再退一个 block。

实测（当前代码，TP2，eager，8192 输入，`--block-size 128` → B=896）：

| 配置 | chunk |
|---|---|
| prefix caching 开（preset 默认） | 5376 / 1792 / 1024 |
| 加 `"disable_eagle_block_drop": true` | 5376 / 2688 / 128（旧结果） |
| `--no-enable-prefix-caching` | 6139 / 2053（"6144 / 2048"） |
| `--block-size 256`（B=1024） | 5120 / 2048 / 1024 |

两组旧数字分别对应 "关了 block drop" 和 "关了 prefix caching"，不是同一配置。

### 结论二：P 不开投机、D 开 DFlash2 不可行

实验：P = Qwen3.8-27B-FP8 无投机，D = + DFlash2，两边 `--block-size 256`，
Mooncake tcp。两边都能启动，请求失败：

```
Mooncake registered group index mismatch for
language_model.model.layers.4.linear_attn: producer=0, consumer=3
```

P 是 4 个 KV group，D 是 15 个（drafter 层加入分组），同一层的 group 编号不同，
`_align_transfer_regions` 拒绝。

即使放宽这项检查也没有意义：DFlash 是 cross-attention drafter，drafter 的
context KV 由 target hidden states 投影得到
（`vllm/v1/spec_decode/dflash.py` `precompute_and_store_context_kv`），
hidden states 不在 KV cache 里。P 不跑 drafter，D 的 drafter 对 prompt 没有上下文，
接受率会归零。

## 2. 方案及效果评估

### 结论三：P/D 同构 + P 多留 draft slot 可行

| 步骤 | P preset | D preset | 结果 |
|---|---|---|---|
| Step 1 | DFlash2，N=6144，bs 256 | 同 P | 传输成功；7038 输入 P chunk 5120/1917；D 只算尾部 1 token；输出与直连 D 完全一致；接受长度 4.68（直连 D 4.81） |
| Step 2 | DFlash2，**N=6149**，bs 256 | N=6144 | 8406 输入 P chunk **6144/1024/1238**；接受长度 4.67；输出与直连 D 一致 |

P 侧带 drafter 的额外开销：5 层 K/V 投影（DFlash2 drafter 为 5 层，hidden 5120）
加首 token 后一次被丢弃的 draft（proxy 把 P 的 `max_tokens` 设为 1）。

Step 2 的第二个 chunk 停在 7168 是 eagle block drop 的效果；是否在 P 上关掉
block drop 未验证，它会影响 D 侧 drafter KV 的完整性。

P/D 两份 preset 见 `vllm_scripts/presets/mpi/dense/dflash/pd_prefill_draft_slot/`
（含运行命令）。`pd_launcher.sh` 新增 `USER_VLLM_PD_PREFILL_PRESET` /
`USER_VLLM_PD_DECODE_PRESET`，P 和 D 可用不同 preset；`PD_PROXY_DESIGN.md` 已补充说明。

## 3. 影响及约束

- P/D 的 KV 布局必须一致：模型、`block_size`、prefix caching / mamba 模式、
  speculative config（含 drafter）。P 不开投机、D 开 DFlash 不可行。
- P 的 `max_num_batched_tokens` 需比 D 多 `num_speculative_tokens`，才能让首个 chunk 与 D 对齐。
- P 侧带 drafter 的额外开销：5 层 K/V 投影加首 token 后一次被丢弃的 draft。
- 未验证：P 上关闭 eagle block drop 对 D 侧 drafter KV 完整性的影响。

## 4. 后续开发

当 `kv_transfer_config.is_kv_producer` 时，让 scheduler 的 `draft_slots` 取 0、
不 propose，但保留 drafter 的 context KV 预计算。P 既能产出可传的 drafter KV，
又没有预留和 propose 开销。改动点：`scheduler.py` 的 `draft_slots`、
`VllmConfig._set_max_num_scheduled_tokens`、model runner 的 propose 入口。

对真实 NPU Infra 团队：

- 若实现 P 侧 `draft_slots=0`，需要在 NPU 侧 scheduler / model runner 保留
  drafter context KV 预计算，同时跳过 propose。
- 不同 P/D 部署规模下，需要确认 Mooncake 传输的 KV group 对齐在 NPU 上同样成立。
