# DeepSeek-V4.1 Engram 拆分（Engram disaggregation）

目标部署形态是 EP48 + 8 个 Engram rank（`20261025_DeepSeek-V4.1-Flash-NPU-parallel-memory-plan.md` 2.3 节）：注意力/EP rank
不再持有 189 GiB 的 Engram 表，表按 hash 列切到 E 个独立 rank 上，每步注意力 rank 发 hash id、Engram rank 返回表行。
本次按插件已有的 AF-EP 形态实现：固定 MPMD MPI world、按 global rank 划分角色、Engram rank 加载权重后进入一个永不返回的
torch_xcpu 算子（纯 C++ 服务循环，Python 只做启动与退出）；注意力侧每步只多一次请求与一次回包。

**本轮执行范围**：代码、单算子/MPI/插件测试与文档已完成；端到端 preset 已写好但**未执行**（用户审阅代码后再跑，步骤见
`docs/upgrade/13-dsv41-engram-disagg.md`）。

## 1. 背景及分析

### 1.1 现状

XCPU 上 Engram 表是普通 device tensor，按 TP（以及节点内 engram DP 组）切分 hash head：每个 engram 层各做一次
`deepseek_v41_engram_lookup`，再经 DP 组 all-gather / TP all-gather 拼回 24 列（`vllm/models/deepseek_v41/common/engram.py`，
插件 `models/deepseek_v41/engram.py`）。DP2/TP2 下节点内只放一份表，但表仍占注意力 rank 的内存，且跨节点 DP 时每节点一份。

### 1.2 通信结构的选择

每步的交换是 A↔E 的二部图：每个 A rank 对每个 E rank 都有一段长度不同的数据（本 rank 的 T 个 token），回包同样按 (e, a)
两两不同。这正是 alltoallv 的模式，与 AF V8 的 dispatch/combine 同构（在 A∪F 全局通信域上做 alltoallv，A→A、F→F 计数为 0），
也是 NPU 通信库最成熟的路径；点对点在 NPU 上支持弱，intercommunicator 没有 HCCL 对应概念，allgather 对回包无用。

决定：**每步恰好两次 `MPI_Ialltoallv`**（A∪E 通信域，A→A、E→E 与反向计数为 0），不做计数交换：

| 阶段 | A 侧发起 / 完成 | 数据 | 计数来源 |
|---|---|---|---|
| 请求 A→E | 第 0 层之前发起（hash 之后，SP 切分之前） | 每个 (A, E) 对一个固定槽 `[tokens \| ids[max_tokens][L][cpr]]` int32，首元素为本步 token 数（可为 0，-1 = STOP） | 两端常量 |
| 回包 E→A | 与请求同时发起（A 的 recvcounts 只依赖自己的 T_a）；第 1 层 embed 时 `MPI_Waitall` 两者 | `tokens × L × cpr` 行，每行 264 B（checkpoint 原始行：256 B E4M3 + 8 B UE8M0） | E 从请求头得 T_a；A 知道自己的 T_a |

按 A=48、max_tokens=1024（SP，B=2048/TP2）计，每个 E rank 每步收 1.2 MB 请求槽，远小于 MoE dispatch，换来少一次纯延迟型集合。

**延迟掩盖（2026-11-04 第三轮，改自阻塞版）**：A 侧在步首一次流任务里连发两个非阻塞集合（请求发送 + 回包接收），第一个 engram
层的 `collect` 才 `MPI_Waitall`，E 侧的 gather 与传输和第 0 层的 attention/MoE 重叠（真实模型第 1 层才用到，第 14 层有 13 层余量）。
E 侧等到请求后 gather，然后把本步回包与下一步的请求接收一起发出、一起等待（gather 已读完 `slots`，下一步请求可以落进来）。
所有 rank 在通信域上按同一顺序发起非阻塞集合（请求 i、回包 i、请求 i+1、…），这是 MPI 非阻塞集合的匹配规则。
两点实现约束：（1）MPI 要求非阻塞集合的 counts/displs 数组在完成前不得修改，所以它们随 `MPI_Request` 一起保存在端点状态
（`EngramExchangeState`）里，不是流任务的局部变量；（2）回包在流任务之外落入接收区，所以 A 侧的收发缓冲区改为**客户端持有的
CPU tensor**（进程生命周期），不再是 mcpu tensor——mcpu 的内存保护只覆盖 launch 区间内的设备内存，异步写入设备 tensor 会被判为
非法访存（或 CMA 失败）。`KernelPointerMemoryGuard` 对非设备指针是 no-op，所以流任务仍可按原样声明这些指针。
Open MPI 默认没有异步进度线程：A 侧没有其他 MPI 调用时，回包的数据搬运实际发生在 `Waitall` 里（CMA 单拷贝，几 MB 量级为亚毫秒），
但请求已在步首送达 E（E 阻塞在集合里推进），E 的 gather 与第 0 层重叠的收益不受影响；EP 配置下 MoE 的 alltoallv 也会推进它。

集合通信要求**每次 forward 都恰好进入一次请求与一次回包**，包括空闲 DP rank 的 dummy run 与 profile/warmup。EP 已让 A rank 逐层
lockstep，这里不增加约束；上游 `DeepseekV4Model.forward` 对 DP 分片表已有同样的机制（`get_engram_dp_size() > 1` 时喂
`dummy_hashes` 并走 `gather_engram_hashes`），拆分模式下重绑这两个名字即复用这条路径。

### 1.3 表切分与线路格式

每个 engram 层的 24 个 hash 列（`EngramLayout.primes` 展平顺序）按列连续切给 E 个 rank（`cpr = 24 / E`，E ∈ {1,2,3,4,6,8,12,24}）：
rank e 持有每层第 `[e·cpr, (e+1)·cpr)` 列的 bucket 行区间 `[vocab_start, vocab_end)`，与现有 TP head 切分同一语义。hash id 为全局行号，
本地行 = id − vocab_start，不在区间内（含 DEAD = −1）返回零行。E 侧只做 memcpy gather（纯内存节点），A 侧解码复用本地 lookup 的
32 维块解码（`simd::mxfp8x32_to_bf16` + 标量回退），远端行与本地 lookup 逐位一致。

### 1.4 并行组合与功能约束

| 维度 | 约束 |
|---|---|
| E | `24 % E == 0` |
| DP | 任意（含多机）；依赖 vLLM DP 既有 lockstep（DP>1 时空闲 rank 必跑 dummy batch） |
| TP | 任意；SP（DP>1 + TP>1 + EP）时每 rank 只请求自己的 token 分片，非 SP 的 TP>1 每 rank 请求全部 token（E 侧流量按 TP 倍重复） |
| EP | 可开可关；v4/v5/v6 后端不受影响（EP 集合在 A 的 `cluster_comm`）；只与 AF-EP（v7/v8）互斥 |
| PP | 仅 PP=1（报错） |
| runner / 执行模式 | V1 / V2、eager / compile 都支持；DSpark 支持（草稿模型无 engram） |
| 报错退出 | `embedding_across_dp`、DBO、PP>1、PD 分离未覆盖、load format 不是 `auto/safetensors/dummy`、`enable_weights_track`、与 AF-EP 同开、非 MPI launcher |
| 强制改写 | `cpu_offload` / `dp_shared_memory` / `use_thp` 关闭（与现状相同） |

## 2. 方案及实现

### 2.1 拓扑与生命周期

```
MPI COMM_WORLD, size = A + E
  [0, A)     ATTN   = DP × TP × PP 个 vLLM worker（mp_rpc 路径；EP alltoallv 仍在 A 的 cluster_comm 上）
  [A, A+E)   ENGRAM = python -m vllm_xcpu_plugin.engram_disagg.server
```

- `ClusterType.ENGRAM = 2`；ENGRAM rank 与 F rank 同样先 `COMM_WORLD.Barrier()` 再 `initialize_mpi_world`。
- 启动期一次 `MPI_Allgather` 校验 `[protocol, world, A, E, role, role_rank, layers, total_cols, cpr, max_tokens 提案, dim, num_embeddings]`，
  任一字段不一致即报错；`max_tokens` 取 A 侧提案（`max_num_batched_tokens`）的最大值，E 提案 0。
- A worker：`init_device` 注册客户端（`bootstrap_engram_client`，含全部配置校验）→ `load_model` 后 `initialize`（先
  `torch.accelerator.synchronize()`）→ `shutdown` 发 STOP（best effort；异常退出靠 launcher 按 run id 清理）。
- E 进程：`mpi4py.rc.finalize = False` → join world → 读 **text_config** 得 `EngramLayout` → `safe_open(...).get_slice(name)[start:end]`
  只读本 rank 行区间（`--load-format dummy` 填 1.0 / 127，与 vLLM dummy 值一致）→ `initialize` → `deepseek_v41_engram_serve`
  阻塞 → 收齐 STOP 后 `cleanup`，不做 Barrier/Finalize 集合，直接退出。
- A 侧权重加载：`EngramAttentionModelLoader`（load format 前缀 `xcpu_engram_`）override `_get_weights_iterator`：含表的 shard
  文件（真实权重为 47/48，其中还有 `wkv/q/k`，不能整文件剔除）用 `safe_open` 逐名遍历并跳过 `engram.embed.{weight,scale}`，其余文件走
  上游 `safetensors_weights_iterator`（保留 EP 专家过滤）。`xcpu_engram_auto/safetensors` 的 `register_model_loader` 在插件入口
  `register_ops` 中导入（与 AF-EP 的 loader 同处）：config 改写发生在 engine 进程，而 `get_model_loader` 在 mp_rpc worker 进程里跑，
  只在 config 路径导入 loader 模块时 worker 会报 `Load format xcpu_engram_auto is not supported`（2026-11-04 真实权重首跑暴露，dummy
  不经过该路径；回归用例 `tests/engram_disagg/test_tables_and_loader.py::test_plugin_entry_point_registers_the_loader_in_a_fresh_process`）。

### 2.2 每步数据流（A 侧）

```
model.forward（eager，SP 切分前）:
  hash = NgramHashState(...)                                     # 不变
  gather_engram_hashes(hash) ──重绑──► client.request(hash)：
       本 rank 的 token 窗口 = Engram._local_kv_tokens 的公式（SP：chunk=ceil(T/tp)，start=min(tp_rank·chunk,T)，local=min(chunk,T−start)）
       deepseek_v41_engram_remote_request：打包 [E][tokens|ids[T][L][cpr]]（流任务）→ 发起 ialltoallv #1（请求发送）
           与 ialltoallv #2（回包接收，recv 为 CPU tensor）（同一流任务）
  prepare_embeddings → no-op
decoder layer 1 / 14（compile 时在 _XcpuDeepseekV41SourceLayers 图内）:
  XcpuEngram.embed：rows = empty[chunk, 24, 256] bf16 → vllm::xcpu_deepseek_v41_engram_embed → XcpuEngram._fill_rows：
       layer_hash_index == 0：deepseek_v41_engram_remote_collect（MPI_Waitall 两个集合，流任务）
       deepseek_v41_engram_remote_decode(rows, recv, layer, local)：rows[:local] 解码，rows[local:] 清零
  kv = wkv(rows); post_wkv                                       # 不变
```

现有路径的 TP all-gather、`_engram_select_rows`、DP 组 all-gather、`staged_rows` 在拆分模式下全部不再使用。每步 A 侧 Engram 相关算子：
`engram_hash`、`engram_remote_pack`、`engram_remote_request_comm`、`engram_remote_collect_comm`、`engram_remote_decode`×2、`engram_post_wkv`×2。

### 2.3 E 侧服务循环（纯 C++，`torch_xcpu_impl::deepseek_v41_engram_serve_impl`）

```
MPI_Ialltoallv 请求 #1（recvcounts[a] = 槽大小常量）→ MPI_Wait
loop:
  T_a = slots[a][0]；任一 −1（STOP）→ 要求全部 A 为 −1，否则报错；退出
  gather：行数按线程连续切分（含跨 A rank），A1 版本提前 8 行 prefetch；id ∈ [vocab_start_l, vocab_end_l) → memcpy 264 B，否则零行
  MPI_Ialltoallv 回包 #2（sendcounts[a] = T_a·L·cpr·264）；MPI_Ialltoallv 下一步请求 #1；MPI_Waitall 两者
```

表为普通 CPU tensor（不进 mcpu 设备、不受内存保护影响），`deepseek_v41_engram_serve` 注册在 CompositeExplicitAutograd 上，在调用线程阻塞运行。
A 侧收发缓冲区是客户端持有的 CPU tensor（见 1.2 的延迟掩盖段）；`collect` / `stop` 只碰这两个 CPU 缓冲区，注册在
CompositeExplicitAutograd 上，仍在当前 mcpu 流上入队。B0 占位留给 NPU 团队（表在设备内存、DMA 引擎批量行读取）。

### 2.5 与 AF-EP 共享的拆分基础设施（2026-11-04 第二轮）

两种拆分都是"一个大 MPI world，按角色切分"，现在共用一层 `vllm_xcpu_plugin/disagg/`：

| 共享件 | 位置 | 使用者 |
|---|---|---|
| world 建立与角色对通信域 | `distributed/mpi_world.py`：`initialize_mpi_world` 在角色 Split 之后，按角色顺序为每个非注意力角色建立"注意力 + 该角色"的 `pair_comm`（所有 rank 走同一组集合，非成员以 `MPI.UNDEFINED` 参与、持有 None） | AF-EP（A∪F）、Engram（A∪E） |
| 会话基类 `PairSession` | `disagg/session.py`：校验"注意力 rank 在前"、算 role_rank、metadata tensor `[protocol, pair_size, pair_rank, A, X, A, role, role_rank]`、`py2f` 句柄、`allgather/allreduce` | `AfV7Session`、`AfV8Session`、`EngramSession` 继承 |
| 客户端注册表 `ClientRegistry` | `disagg/registry.py` | `af_ep/attn/runtime.py`、`engram_disagg/attn/runtime.py`（公开函数名不变） |
| 对端进程骨架 `run_role_service` | `disagg/service.py`：join world（Barrier → `initialize_mpi_world`）、加载失败 `Abort`、serve、可选 Barrier + Finalize | `af_ep/moe/runner.py`（finalize）、`engram_disagg/server/runner.py`（不 finalize） |
| MPMD 模板 | `serve/serve_mpmd_mp_rpc_all_mpi_template.sh`：rank `[0,A)` 注意力、`[A,A+F)` F、`[A+F,A+F+E)` E，F/E 可为 0；旧的 `serve_afd_*` / `serve_engram_*` 模板改为包装 | 全部 AFD / Engram preset |

由此 A + F + E 可以共存：两种拆分各自在自己的角色对通信域上交换，metadata 的 world_size/rank 都是角色对内的值，C++ 端点不需要改
（它们只校验 comm 与 metadata 一致）。原先 `platform.py` / `config.py` / bootstrap 中的 AF-EP 与 Engram 互斥检查已删除。
worker 侧仍是两个客户端各自 bootstrap / initialize / shutdown（顺序：AF 先于 Engram）。

C++ 公共头（metadata 解析、零计数 alltoallv、初始化 allgather）暂不合并：AF V7/V8 已验收，改动需重跑其验收矩阵；Engram 侧的
`csrc/deepseek_v41/engram_remote.cpp` 自带一份，AF 升级时再迁。

1. `Load format xcpu_engram_auto is not supported`：loader 注册只在 config 路径导入，worker 进程没有执行；已改为在插件入口

## 4. 影响及约束

- 非拆分模式路径不变：`get_engram_client()` 为 None 时所有 override 退回上游实现；`engram_lookup` 只是改用共享解码头（测试通过）。
- `get_engram_dp_size` 的重绑只影响 `nvidia.model` 内的名字（`common.engram` 自己的导入不变），拆分模式下返回 2 仅用于选中 forward 的
  dummy 分支；E=1 时同样成立。
- `launcher_common.sh` 的 run-id 清理分支现在对 AF-EP 与 Engram 拆分都生效，`VLLM_AF_RUN_ID` 前缀分别为 `afd_` / `engram_`。
- 固定 world、best-effort STOP：与 AF-EP 相同，不承诺运行期故障恢复。
- A 侧 `max_tokens` 提案直接用 `max_num_batched_tokens`（SP 下是上界），槽略大但省去 SP 判定。
