# DeepSeek-V4.1 EngramParallel：EP 域全量 rank 二维表分片

日期：2026-11-20
状态：已实现并在单机 `DP=2, TP=2 (EP=4)` dummy（eager + `DYNAMO_TRACE_ONCE` compile）及 `EP32/48/64` 算子级单测验证

## 1. 背景与动机

根据 `docs/models/deepseek-v4.1-flash/20261025_DeepSeek-V4.1-Flash-NPU-parallel-memory-plan.md` 的内存估算，DeepSeek-V4.1-Flash 的两个 Engram 层（第 1 层与第 14 层）合计约 **188.83 GiB**（每层 24 个素数子表，合计 48 个物理子表，每行 256 字节 FP8 值 + 8 字节 UE8M0 scale = 264 字节）。

此前已实现的 **Engram Disaggregation**（`VLLM_XCPU_ENABLE_ENGRAM_DISAGG=1`）需要额外的专用 Engram MPI 节点、MPMD 启动模板（`serve_mpmd_mp_rpc_all_mpi_template.sh`）以及整除 24 的 Engram rank 数约束。若将 Engram 表直接二维切分并常驻在全部 $N = \text{DP} \times \text{TP}$ 个模型 worker rank（即 EP 域）中，单 rank 表显存降为：

- `EP32`：约 **5.90 GiB / rank**
- `EP48`：约 **3.93 GiB / rank**
- `EP64`：约 **2.95 GiB / rank**

无需专用 Engram 节点，沿用单角色 MPI 启动模板（`serve_mp_rpc_all_mpi_template.sh`）即可运行，同时支持任意 `world_size >= 1`（包括 32、48、64）。与 `VLLM_XCPU_ENABLE_ENGRAM_DISAGG=1` 互斥（启动配置与 worker 初始化均直接报错拒绝同时开启）。

## 2. 二维 `(column-group × row-range)` 静态分片设计

### 2.1 分片拓扑 (`EngramParallelLayout` / `EngramParallelLayoutSpec`)

将 `L` 个 Engram 层、每层 `C` 个 hash 列展平为 `M = L * C` 个连续素数子表，构造全局有效行空间 `[0, sum(active_rows))`。对于任意进程数 `N = world_size`：

$$G = \gcd(M, N), \quad K = \frac{N}{G}$$

- 将 `M` 个子表等分为 `G` 个列组，每组包含 `M / G` 个连续子表。
- 每个列组内的行区间 `[group_start, group_end)` 再按 `K` 等分切成连续的 `[rank_cuts[r], rank_cuts[r+1])`（第 `g` 组对应 rank `[g*K, (g+1)*K)`）。
- 典型配置（`L=2, C=24, M=48`）：
  - `N=4`：`G=4, K=1`，每 rank 持 12 列完整行；
  - `N=32`：`G=16, K=2`，每组 3 列切 2 份，`max_cols_per_rank <= 2`；
  - `N=48`：`G=48, K=1`，每 rank 恰好持 1 个素数子表（`max_cols_per_rank = 1`）；
  - `N=64`：`G=16, K=4`，每组 3 列切 4 份，`max_cols_per_rank <= 2`。
- 允许某个 `(layer, rank)` 切片为空（`lo == hi == 0`），此时设备侧表切片形状为 `(0, 256)` FP8 / `(0, 8)` UE8M0，`gather_kernel` 对空 slice 指针保留 `nullptr` 防护。

### 2.2 请求容量上界保证（热点不溢出）

单步内每个本地 token `t` 的每个 `(layer, c)` 查询最多只能落到该列所跨越的唯一一个 owner rank。记单个 rank 所属行区间最多跨越 `max_cols_per_rank` 列，则本 rank 向任意对端 `p` 发送的查询数上界严格不超过：

$$\text{max\_q} = \text{max\_tokens} \times \text{max\_cols\_per\_rank}$$

即使 batch 内全部 token 与全部 n-gram 命中相同热点行，请求计数也不会溢出。在开启 Sequence Parallelism（SP）时，`EngramParallelClient.initialize()` 将本 rank 提交给 `MPI_Allgather` 协商的 `max_tokens_proposal` 按 `ceil(proposal / tp_size)` 缩放，使所有 rank 的交换缓冲区容量减半。

## 3. 每步两集合通信协议（`torch_xcpu`）

实现位于 `torch_xcpu_impl/include/deepseek_v41/engram_parallel.h`、`torch_xcpu_impl/src/deepseek_v41/engram_parallel.cpp` 及 `torch_xcpu/csrc/deepseek_v41/engram_parallel.cpp`：

1. **初始化与握手 (`deepseek_v41_engram_parallel_initialize`)**：
   - 使用从 `mpi_world.cluster_comm.Dup()` 复制的独立通信域。
   - 通过 `MPI_Allgather` 校验 `world_size`、`layers`、`total_cols`、`head_sizes_flat`、`num_embeddings`、`(dp_size, tp_size, use_sequence_parallel)` 与 `(dp_rank, tp_rank)` 网格一致性，并协商全局 `negotiated_max_tokens = max(proposal)`。
   - 在客户端分配 CPU 长生命周期交换缓冲区：`req_send` / `req_recv` (`[W, 1 + max_tokens * max_cols_per_rank] int32`)、`reply_send` / `reply_recv` (`[W, max_tokens * max_cols_per_rank * 264] uint8`) 与 `reply_index` (`[max_tokens, L, C] int32`)。

2. **前向起点异步发起请求 (`deepseek_v41_engram_parallel_request`)**：
   - 由复用的 `model.py::gather_engram_hashes`（及 compiled 分支与 `get_engram_dp_size() -> 2` 路由的 `dummy_hashes` 分支）在 Layer 0 之前调用一次。
   - `pack_kernel`（`tokens < 128` 串行，`>= 128` 两段确定性 OpenMP 并行）将 `[token_start, token_start + num_tokens)` 内有效 hash id 映射到全局行号与 owner rank `p`，填入 `req_send[p]`（首元为计数 `count`），对越界/DEAD_ID 将 `reply_index` 置 `-1`。
   - 利用 `ForwardContext.dp_metadata.num_tokens_across_dp_cpu`（`DP == 1` 时取本地 token 数）结合静态 `cols_per_rank[j]` 计算每对请求上限 `0`（当 `tokens == 0` 或 `cols_per_rank[j] == 0`）或 `1 + n_i * cols_per_rank[j]`，以固定槽位偏移发起非阻塞 `MPI_Ialltoallv(req_send, ..., req_recv, ...)`（无需额外同步 `Alltoall`），与 Layer 0 计算重叠。

3. **首个 Engram 层等待、Gather 与精确字节应答 (`deepseek_v41_engram_parallel_collect`)**：
   - 任务 1：`MPI_Waitall` 完成异步请求通信。
   - 任务 2：`launch_gather_kernel` 在 `MCPU_LAUNCH_TIMED_KERNEL` 与 `at::mcpu::KernelPointerMemoryGuard` 保护下按 rank 解析 `req_recv` 计数，从本 rank 的 `mcpu` 设备切片读取 256B E4M3 weight + 8B UE8M0 scale 到 `reply_send`（A1 带 AVX-512 prefetch，A0 标量参考实现）。
   - 任务 3：两侧已知精准收发条数（无需额外 count 交换），直接执行 `MPI_Alltoallv(..., MPI_BYTE)`，只传输实际命中的 `count * 264` 字节。

4. **各 Engram 层解码 (`deepseek_v41_engram_parallel_decode`)**：
   - 在自定义透明算子 `torch.ops.vllm.xcpu_deepseek_v41_engram_embed` 内由 `XcpuEngram._fill_rows -> EngramParallelClient.fill_rows` 触发（仅 `layer_hash_index == 0` 调用 `collect`，后续层直接复用 `reply_recv`）。
   - 调用 `engram_row_decode.h` 将 264B 原始记录解码为 BF16 并写入输出缓冲，超过 `num_tokens` 的 SP padding 尾行和 `reply_index < 0` 行清零，保证 eager 与 `DYNAMO_TRACE_ONCE` (`mode: 3`) 编译图路径完全共用。

## 4. 插件集成、流式切片加载与上游契约

- **配置与互斥** (`vllm_xcpu_plugin/envs.py`, `models/deepseek_v41/config.py`)：
  - 新增 `VLLM_XCPU_ENABLE_ENGRAM_PARALLEL`（默认 `0`）。
  - 抽取 `_update_distributed_engram_config` 统一校验 DeepSeek-V4.1、`VLLM_CPU_USE_MPI=1`、非 `embedding_across_dp`、关闭 `cpu_offload`/`dp_shared_memory`/`use_thp`，并将非 dummy 的 `auto`/`safetensors` 重写为 `xcpu_engram_parallel_{auto,safetensors}`。与 `VLLM_XCPU_ENABLE_ENGRAM_DISAGG` 互斥。
- **Worker 与模型嵌入适配** (`worker/worker_v1.py`, `models/deepseek_v41/engram.py`, `engram_parallel/{bootstrap,session,client,layout}.py`)：
  - `McpuWorker.init_device` 注册 `EngramParallelClient`；`load_model` 读取模型构造后的 `DeepseekV4Model.engram_layout` 完成 `EngramParallelSession.initialize`。
  - `XcpuEngram._create_embedding` 通过 `client.prepare_embedding(layout, layer_hash_index)` 传递层索引；`XcpuParallelEngramEmbedding.__init__` / `_get_shard_info` / `_allocate_weights` 旁路上游列分片，按 `[lo, hi)` 分配本地行数并在 `super().__init__` 后更新 `vocab_start_idx`/`vocab_end_idx` 与 `param.engram_vocab_start = lo`。
  - `_engram_parallel_weight_loader` 同时支持 `EngramParallelModelLoader` 预先切片的张量、`0:0` 空切片以及 `DummyModelLoader` 传入的整表张量（通过 `narrow(0, param.engram_vocab_start, part_rows)` 裁剪）。
- **流式权重分片加载器** (`engram_parallel/model_loader.py`)：
  - 仅在 `safetensors` 索引指明的含 Engram 表 shard 中遍历，`safe_open(...).get_slice(name)[lo:hi].contiguous()` 仅将本 rank 切片读入内存，邻近非表权重仍执行 `should_skip_weight(..., local_expert_ids)` 过滤；其余不含表的 shard 直接走标准 `safetensors_weights_iterator`。
- **上游契约 (`vllm_xcpu_plugin/models/deepseek_v41/upstream.py`)**：
  - 未修改 `vllm` 仓库代码；所有新增站点均已登记到 `deepseek_v41.engram.remote` 与 `deepseek_v41.engram.no_offload`。
