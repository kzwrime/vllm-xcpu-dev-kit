# GLM-5.2 AFD 适配与 DFlash2 兼容（vLLM 0.31）

## 1. 背景及分析

### 1.1 目标

- GLM-5.2-FP8（ZhipuAI，704 GiB）与 GLM-5.2-MXFP4（amd，408 GiB，XCPU 走 W4A16）在 AFD 模式下数值正确；
- AFD 与 DFlash2 草稿（incoai/GLM-5.3-DFlash2，4.6 GiB）兼容；
- 本机 1007 GiB 内存，测试过程不得爆内存；全过程留档，记录观察到的优化点。

### 1.2 基线

| 仓库 | 基线 |
| --- | --- |
| vLLM | `dbb08efac2`（dev/0.31，未改动） |
| vllm-xcpu-plugin | `55ba8cd`（dev/0.31） |

### 1.3 0.31 上 GLM AFD 的缺口（代码审查结论）

AFD 在 0.31 只验证过 Qwen3 系列。GLM5.2 走 `DeepseekV2Model`，与 Qwen3 有三处不同，直接导致真实权重 AFD 无法启动或拒绝 DFlash2：

| # | 位置 | 现象 / 原因 | 影响 |
| --- | --- | --- | --- |
| G1 | A 侧权重加载 | `DeepseekV2Model.load_weights` 通过 `expert_params_mapping` 直接 `params_dict[name_mapped]` 查找 `w13_weight` 等专家参数；A 侧 `RemoteExpertsFusedMoEMethod.create_weights` 不创建任何专家参数，→ `KeyError`。Qwen3 走 `experts.load_weights()`，插件的 `skip_checkpoint_weights` 能拦截，GLM 不经过这一入口。 | 真实权重 A 启动失败（dummy 不调用 `load_weights`，因此 dummy preset 能跑） |
| G2 | F 侧权重加载 | GLM checkpoint 带 MTP 层 `model.layers.78.*`（`num_nextn_predict_layers=1`），F 的 `RoutedExpertsWeightLoader` 判定 layer 78 不是 MoE 层 → `ValueError("routed weight belongs to a non-MoE layer")` | 真实权重 F 启动失败 |
| G3 | A 侧兼容性检查 | `compatibility.py` 对任意 `speculative_config` 拒绝 | DFlash2 无法与 AFD 同时启用 |

G1/G2 在 0.25-v3 工作区已有对应修复（插件提交 `7096fc1` 的 F 侧 `skip_spec_layers`；未提交的 `af_ep/attn/model_loader.py` A 侧 loader），本轮移植到 0.31 并做了调整（见 2.1）。

`routed_scaling_factor=2.5` 已核对：0.31 中 `apply_routed_scale_to_output=False`，缩放在 A 侧 router 写入 top-k 权重，随 `topk_weights` 发给 F，AFD 路径不会遗漏。

DFlash2 草稿为 dense（`model_type=qwen3`，6 层，无 routed experts），只读取目标模型 aux hidden states；目标模型每步仍按层序进入每个 MoE 层一次，F 的“每 pass 遍历全部 MoE 层”合同不变。GLM MTP 草稿复用 layer 78 的 MoE，F 不加载，仍需拒绝。

### 1.4 内存预算

| 组件 | FP8 | MXFP4 |
| --- | --- | --- |
| checkpoint | 704 GiB | 408 GiB |
| A（非 routed 专家，TP1） | 约 40 GiB（待实测） | 约 36 GiB（0.25-v3 TP2 实测每 rank 18 GiB） |
| F（routed 专家合计） | 约 660 GiB | 约 370 GiB |

AFD 不复制权重（A 只持非专家，F 按 EP 切分），总量与串行 TP1 相同；串行 FP8 TP1 已在 2026-10-14 跑通。真实权重一律使用 A1（DP1/TP1）+ F2，不使用会复制 A 权重的 DP>1 拓扑；每次启动前检查 MemAvailable，运行中 2 s 采样，低于 32 GiB 即终止整个进程组（驱动 `run_afd.py` 内置）。

### 1.5 DFlash2 在 0.31 上的额外缺口（运行中发现）

dummy 冒烟显示 DFlash2 的阻塞不在 AFD，而在 0.31 的 GLM 串行路径本身：

| # | 现象 | 原因 |
| --- | --- | --- |
| D1 | 启动即 `NotImplementedError: XCPU v0.31 sparse MLA speculative decoding is not validated` | `attention/sparse_mla.py::validate_sparse_config` 对任何 `speculative_config` 拒绝（0.31 MLA 重组时加入的保守门禁）。串行 DFlash2 preset 在 0.31 同样不可用。 |
| D2 | 解除 D1 后首个请求 HTTP 500：`Fake Triton kernel is not registered: ...indexer.PrepareUniformDecodeKernel.kernel`；compile 在启动预热即失败 | 目标模型验证步每个请求 1+k=6 个 token。CPU 上 `_supports_native_decode(6)` 为 False，indexer 走 flattening 分支；长度一致时调用 Triton `PrepareUniformDecodeKernel`，插件未提供替代实现 |

D1 解除前核对：indexer C++ 镜像已含 padded/flattened decode（torch_xcpu `4700efa`），10-14 记录中被排除的 8 个 padded speculative 用例现已通过，`test_indexer_core/decode_metadata/prefill_metadata` 共 50 项全部通过；0.31 上 `supports_varlen=False`，`decode.indices=None`，不会进入插件拒绝的 varlen 路径。稀疏 MLA 本身逐 token 使用 indexer 输出的 top-k，验证 token 走 prefill 调度不影响语义。

### 2.2 验证方法

驱动 `vllm_scripts/logs/glm52-afd-20261015/run_afd.py QUANT MODE KIND TOPO SPEC`：按参数生成 preset（`<label>.sh`）、启动服务、发送请求、记录响应及 logprob，并内置内存守护（每 2 s 采样 MemAvailable，低于 32 GiB 杀整个进程组）。`run_matrix.sh` 串行执行，`compare.py` 逐 token 比较（相同前缀长度、前缀上的最大 |Δlogprob|、DFlash 接受率）。

- AFD 拓扑：A = DP1/TP1（1 rank），F = EP2（2 rank），共 3 个 MPI rank；默认 V8，另测 V7。
- 对照 ref：同一代码、同一参数的非 AFD 串行 TP1（`--launcher mp`）。
- 共同参数：max_model_len 4096，max_num_batched_tokens 256（dummy 32），FP8 KV cache，seed 42，temperature 0，关闭 thinking。
- 请求：真实权重复用 `serve_test/test_glm52_serial.py`（math、capital、2134 token 长输入检索、长前缀重复、ragged completion batch），再加 5 路并发中文长回答（每路 64 token）；dummy 用 ignore_eos 固定长度请求。
- DFlash2：`num_speculative_tokens=5`，草稿 greedy，草稿 KV BF16（与串行 preset 一致）。dummy 用 `dummy-dflash2-draft/config.json`（target_layer_ids 改为 0–5，适配 7 层）。

| 对照（真实 MXFP4，同一请求集，含 solo） | 相同前缀 | 最大 Δlogprob |
| --- | --- | ---: |
| 串行 vs 串行（重复运行） | 352/352 | 0 |
| AFD EP2 vs AFD EP2（重复运行） | 352/352 | 0 |
| 串行 vs AFD EP2 | 283/432，c3 单独发送也在第 36 token 分叉 | 0.462 |

两侧各自完全确定。逐用例拆开看 EP1（单 F 持有全部 256 个专家）：

| 用例（串行 vs AFD EP1，78 层真实 MXFP4） | 非零 Δlogprob 的 token |
| --- | --- |
| math、capital、long（2134 token，走 sparse top-k）、prefix-repeat、batch×2、solo0、solo1、c3-solo（64 token） | 全部 0（逐位一致） |
| c0–c4（5 路并发） | 从第 0 个 token（prefill）起即不同 |

8 层截断模型上同样：AFD EP1 与串行在所有确定性用例上逐位一致，唯一差异是 3-prompt batch，而该用例在串行自身重复运行之间也不一致。

结论：

- **AFD 的路由、传输、F 计算与 A 侧合并在数值上精确等价于串行**（EP1 逐位一致）。F 的 `fused_moe_compute_ep_<Backend>` 与串行 `fused_moe_compute_<Backend>` 是同一 `run_fused_moe_compute` 流水线（`torch_xcpu/csrc/fused_moe_compute.cpp`）；A 侧 router 与 `moe_scaled_add`（施加 `routed_scaling_factor=2.5`）与串行同一代码。
- 并发用例的差异来自 prefill 分组：AFD 的单步时延不同，5 个请求到达后被分进不同 prefill 步，batch 形状改变归约顺序；与 AFD 数学无关。
- EP2 在确定性用例上也有差异：每个 F 把本地专家的加权部分和以 BF16 发回，A 在 FP32 中累加两个部分和后再转 BF16（`fused_af_a_dispatch_combine_v8.cpp`），比串行多一次 BF16 舍入。这与普通 EP（V5/V6 按目的 rank 局部归约后求和）同类，属设计差异；对任务准确率的影响用 GSM8K 配对评测验证（`gsm8k_paired.py`，复用 `vllm/tests/evals/gsm8k/gsm8k_eval.py` 的 5-shot 提示词与答案解析，逐题保存），见 2.4.5。
