0 执行摘要与核心决策建议

随着超大规模稀疏 MoE 大模型成为生产主力——例如总参数约 744B（每 Token 激活约 40B，78 层、256 专家）的 GLM-5.2 / GLM-5.3[15][16]，以及骨干参数约 552B（Prefill 激活 ~8B / Decode 激活 ~16B，40 层、384 专家）外加 196B 稀疏查表 Engram 条件记忆（合计 ~748B）的 DeepSeek-V4.1-Flash[14][20]——大模型推理的系统瓶颈已从纯计算全面转向显存容量与权重访存带宽墙（Memory Wall）。与此同时，AI 算力生态进入多格式并行代际：上一代硬件以原生 FP8/INT8 矩阵乘搭配软件块缩放为主，新一代旗舰（NVIDIA Blackwell B200、AMD MI350X、华为昇腾 950）则向硬件原生支持 OCP 微缩块缩放（UE8M0 + MXFP8 / MXFP4）演进[1][2][4]。

核心立项结论（面向管理层决策与矩阵乘团队）
  • 为什么不直接走 FP8 软件解包？在主打 BF16 矩阵核、缺乏硬件原生 FP8 矩阵指令的目标 NPU 上，FP8（E4M3FN）反量化到 BF16 存在 4-bit 指数重偏置、Subnormal（exp=0 含 7 档非零幅值，需 8 项查表/分支）以及 FP32 块缩放乘法等重开销，实测 [512, 128] Tile 耗时约 ~7,000 cycles；改用离线转换的标准补码 Int8 + UE8M0 后，已在真实 NPU 确认通过 4 步向量指令流将反量化压至 1,500~2,000 cycles，且数学上对 BF16 为 100% 零舍入精确表示[18]。
  • 算子契约面向 GLM-5.3 与 DeepSeek-V4.1-Flash 统一设计：GLM-5.3（~744B）原生采用 FP8 [128,128] FP32 Scale，DeepSeek-V4.1-Flash（~552B 骨干 + 196B Engram）的 Dense/Attention/Engram 投影层原生采用 FP8 [32,32] UE8M0（MoE 专家为 MXFP4）[14][19]。矩阵乘团队仅需实现一套参数化支持 [16,16] / [32,32] 的 Int8 + UE8M0 算子契约，即可在完成 GLM-5.3 落地后平滑复用至 DeepSeek-V4.1-Flash 的 FP8 投影层（注：本文第 5.2–5.3 节定量实测均基于 GLM-5.2 权重，DeepSeek-V4.1-Flash 精度需在后续阶段独立验证）。
  • 长期路线零技术债：采用标准二进制补码 torch.int8 + OCP 开放标准 UE8M0，既在当前 W8A16 路径上实现极速反量化，又完整保留未来无缝切换至硬件原生 INT8 / MXINT8 W8A8 矩阵核的演进通道，避免私有非标编码（如 S1M7、E2M5）带来的生态锁死[17]。

1 大模型量化演进与现状总览

大模型自回归推理天然分裂为两个物理瓶颈迥异的计算阶段：Prefill（首字填充阶段）输入序列长、批处理有效维度 M 大，属于典型的计算受限（Compute-bound）；而 Decode（逐 Token 生成阶段）每步仅处理少量 Token，算术强度（FLOPs/Byte）极低，每生成一个 Token 都必须把庞大的活跃权重从 HBM 搬运至片上缓存，属于极端的显存带宽受限（Memory-bandwidth-bound）。

进入 MoE 时代后（如 671B 的 DeepSeek-V3[11]、~744B 的 GLM-5.3[15]、~552B 骨干 + 196B Engram 的 DeepSeek-V4.1-Flash[14]），超过 95% 的参数沉淀在稀疏路由专家与条件记忆表中。将权重从 16-bit（BF16）压缩至 8-bit 乃至 4-bit，已成为降低部署卡数、突破 HBM 带宽墙与翻倍峰值算力密度的必由之路。纵观过去四年，工业界量化体系经历了三代清晰演进：

第一代：粗粒度整数 PTQ 2022–2023

代表格式：INT8 / INT4（Per-Tensor、Per-Channel 或 Group-128 FP16 Scale）

特征：以 GPTQ[6]、SmoothQuant[7]、AWQ[8] 为代表，对已训练好的 FP16/BF16 模型执行事后压缩。因粗粒度下激活异常值难处理，生产落地多以 W4A16 省显存为主。

第二代：细粒度块缩放 FP8 2024–2025

代表格式：FP8 E4M3FN + 权重 [128,128] / 激活 [1,128] FP32 Scale

特征：由 DeepSeek-V3[11] 在 Hopper 架构上确立（算子层由 DeepGEMM / CUTLASS 实现软件块缩放[12]）。原生 FP8 预训练产出无损 8-bit 权重，被 GLM-5 系列[15]、Qwen3 等广泛采纳。

第三代：OCP 微缩块缩放（MX） 2025–2026+

代表格式：UE8M0 纯指数 Scale + MXFP8 / MXFP4 / NVFP4 / MXINT8[1]

特征：以 16~32 元素极小块隔离离群值，并用 1 字节纯 2 的幂次缩放替代 4 字节 FP32 Scale；由 Blackwell tcgen05[2]、CDNA4 v_mfma_scale[4] 及昇腾 950 原生硬件承接，支撑 DeepSeek-V4 混合精度（Dense FP8 + MoE MXFP4）[14]。

2 主流低精度数据格式解析（位级结构与横向对比）

低精度格式的设计本质是在有限比特数内权衡动态范围（指数位 Exponent）与相对精度（尾数位 Mantissa）。在开放计算项目 OCP 制定的 Microscaling Formats（MX）规范[1]中，动态范围的职责被剥离给一组元素共享的 UE8M0 块缩放指数，从而大幅释放单个数据元素的有效位宽。

核心数学洞察：为何小块 Int8 的数值精度反而显著高于 FP8（E4M3FN）？

直觉常认为“浮点（FP8）比整数（Int8）更准”，但这仅在粗粒度大动态范围下成立。8-bit 总预算中，FP8 花费 4 bit 存独立指数，只剩 3 bit 尾数，导致无论块切得多细，FP8 每个元素的相对舍入步长始终卡死在 2−3/2 = 6.25%（对应权重均方根误差地板 ~2.65%）。反观补码 Int8 将全部 7 bit 幅值用于线性精度，块内相对误差满足 RelRMSEint8 ≈ CF / (√12 · Qeff)：只要用 [16,16] 或 [32,32] 小块将峰值因子 CF = amax / rms 压至 3~4 左右，Int8 相对误差即降至 0.9%~1.7%，全面反超 FP8[17]。

3 大模型量化方法体系详述（分维度拆解）

业内常将“预训练量化、QAT、PTQ、离线/在线、W8A16/W8A8、AWQ/GPTQ/SmoothQuant/QuaRot”混谈。从工程视角看，它们实际分属四个相互正交的维度：何时介入（生命周期）、量化对象（W/A 组合）、定标时机与粒度以及异常值抑制算法。

3.1 维度一：按介入阶段划分（预训练量化 vs QAT vs PTQ）

  1. 原生低精度预训练（Native Low-Precision Pre-training）： 模型原厂在万亿级 Token 预训练全程直接使用 FP8 或 MXFP4 执行前向/反向矩阵乘，同时在优化器中保留 FP32 主权重（Master Weights）。典型代表如 671B DeepSeek-V3 的细粒度 FP8 预训练[11]。优势是原生无损且加速训练；门槛在于极高算力与语料成本，仅模型原厂可为。
  2. 量化感知训练 / 微调（QAT / QAFT）： 在已训模型计算图中插入“伪量化节点（Fake Quant / QDQ）”，利用直通估计器（STE）继续微调模型权重以适应截断噪声。优势是在 4-bit 等极限低比特下显著挽回精度；代价是仍需完整训练框架与显著 GPU 机时。
  3. 训练后量化（PTQ, Post-Training Quantization）： 无需反向传播重训，直接对已发布权重（BF16 或 FP8）离线转换，是推理引擎与芯片适配最主流的手段。按是否需要样本数据分为：
    • 零数据离线 PTQ（Data-free）：仅依据权重自身数值分布做小块取整或块内 MSE 搜索（单机多线程即可快速完成 700B 模型转换，无校准集过拟合风险）。
    • 校准集 PTQ（Calibration-based）：用数百条代表性文本跑前向推理，统计激活通道分布以指导权重保护或误差补偿（如 GPTQ、AWQ、SmoothQuant），主要用于 4-bit 权重或粗粒度 W8A8。

3.2 维度二与三：W/A 计算形态、离线/在线定标与 KV Cache 量化

W8A16 vs W4A16（Weight-Only 权重量化）

  • 计算方式：权重以 8-bit/4-bit 存放在 HBM 中，加载至片上后通过 SIMD/向量单元实时反量化为 BF16，再送入 BF16 矩阵核与 BF16 激活相乘。
  • 适用价值：直击 Decode 阶段与 MoE 权重的显存容量和带宽瓶颈；因激活不量化，彻底避免激活离群值导致的精度塌陷，上线风险最低。
  • 关键指标：反量化指令周期能否足够低，不被向量单元拖成新瓶颈——这正是本方案第 5 节验证的核心突破点。

W8A8 vs W4A4（权重 + 激活双量化）

  • 计算方式：权重离线量化；激活在推理时在线动态量化（Online Dynamic）（按 Token/Block 实时求 amax 算 Scale），直接送入硬件原生 8-bit/4-bit 矩阵核。
  • 适用价值：除压缩显存外，更能在 Prefill 或大 Batch 算力受限阶段让矩阵核峰值算力成倍提升（FP8/INT8 2×、FP4 4×）。
  • 前提条件：强依赖硬件提供原生低比特矩阵乘与（在 4-bit/微缩场景下的）硬件块缩放指令。

正交优化——KV Cache 量化：在长上下文（128K–1M）和高并发 Serving 中，历史 KV Cache 会迅速挤占显存。KV Cache 量化（如 DeepSeek/GLM MLA 架构下的 fp8_ds_mla 及本套件已支持的 int8_ds_mla，单 Token 均为 656 字节[17]）与权重量化相互正交，可直接叠加启用。

4.2 关键硬件概念澄清：Hopper 软件块缩放 vs Blackwell tcgen05 硬件块缩放

严防软硬件混淆：为什么不能说“H100/H200 原生支持 Block FP8”？
  • NVIDIA Hopper（H100/H200, SM90）仅硬件原生支持无缩放 FP8 WGMMA，不支持硬件 Block Scale：Hopper 的 wgmma.mma_async 指令直接接收 FP8 矩阵片段执行 FP8 × FP8 → FP32，指令本身没有任何 Scale 操作数端口。更关键的是，DeepSeek-V3 技术报告[11]与 DeepGEMM[12] 的实测揭示：Hopper FP8 WGMMA 内部采用低位宽定点累加器，仅保留对齐后最高的约 14-bit 有效精度。因此，DeepSeek-V3 与 GLM-5 所采用的 [128,128] 权重块 + [1,128] 激活块 FP32 Scale 完全是算子库（CUTLASS / DeepGEMM）在软件层编排的——每跑完 4 次 K=32 的 WGMMA（即每 128 个 K 元素），由 CUDA Core 软件将中间结果提升（Promotion）到高精度 FP32 累加器，并在软件端乘上 FP32 Block Scale。
  • NVIDIA Blackwell（B200/GB200, SM100）才真正把 Block Scale 硬件化：Blackwell 引入第 5 代 Tensor Core 指令 tcgen05.mma（例如 tcgen05.mma.cta_group.kind::mxf8f6f4.block_scale 与 kind::mxf4nvf4.block_scale）[2]。该指令由单线程发射，直接从专用片上 Tensor Memory (TMEM) 消费权重/激活及其对应的块缩放张量（SFA/SFB，即 UE8M0 或 E4M3），在硬件矩阵核内部一步完成缩放累加，不再占用 CUDA Core 执行周期性软件 FP32 乘加（AMD CDNA4 的 v_mfma_scale_* 同理[4]）。

为什么 GLM-5.3（~744B）沿用 FP8 [128,128] FP32 Scale？

  1. 最大化兼容存量 Hopper 集群与软件生态：[128,128] FP32 Scale 与 DeepSeek-V3[11] 在 DeepGEMM / CUTLASS / vLLM / SGLang 上打磨最久的 Hopper 软件分块缩放内核完全一致，能够零摩擦覆盖当前占比最大的存量 H100/H200/H800 部署池。
  2. 稳态 8-bit 精度风险最低：GLM-5.2 / 5.3（78 层、256 专家，主打复杂 Coding 与 Agentic 工程能力[15]）全量保持 8-bit 权重，规避了 4-bit 混合精度训练或 QAT 可能引入的推理长尾波动与工程调优成本。

为什么 DeepSeek-V4.1-Flash（~552B+196B）转向 FP8 [32,32] UE8M0 + MoE MXFP4？

  1. 明确面向新一代国产与国际多硬件公约数（实证 + 架构分析）：DeepSeek 在 2025 年发布 DeepSeek-V3.1 时即在官方 HuggingFace 仓库明确声明 “UE8M0 FP8 is designed for soon-to-be-released next-generation domestic chips”[13]。到 V4.1-Flash[14]，MoE 进一步引入 OCP MXFP4（UE8M0）——该标准恰好同时被 NVIDIA B200（tcgen05）[2]、AMD MI350X（v_mfma_scale）[4] 与华为昇腾 950 纳入原生支持版图；拒绝 NVIDIA 私有 NVFP4 避免了单一供应商锁定。
  2. 同时兼顾存量 H200 显存与带宽红利：384 专家 MoE 权重压至 MXFP4（4.25 bit/参数）后，即便在无原生 FP4 算力的 H200 上，Decode 阶段通过 W4A16 融合反量化依然可将权重搬运带宽减半、显著缩减单实例部署卡数。
  3. 分级精度保护：参数占比小但极敏感的 Attention / Dense / Engram 层保留 FP8 [32,32] UE8M0（二维块保持转置不变性，且 UE8M0 消除 FP32 乘法），守住 1M 长上下文与复杂推理精度底线[14][19]。

5 本平台推进 Int8 + UE8M0 离线量化方案的系统论证

回到本平台的真实硬件边界：当目标 NPU 主力矩阵核为 BF16（不具备硬件原生 FP8/FP4 矩阵乘指令，且软件解包 FP8 代价高昂）时，直接在线消费 FP8 权重会使向量单元成为严重瓶颈。因此，我们将源模型（GLM-5.3 的 FP8/BF16 或 DeepSeek-V4.1-Flash 的 FP8 层）离线转换为标准二进制补码 Int8 [-128, 127] + UE8M0 块缩放（推荐 [16, 16]，兼容 [32, 32]），执行 W8A16 极速反量化矩阵乘[17][18]。

5.1.1 离线量化与推理反量化参考实现（Python / PyTorch）

为了便于矩阵乘算子团队与评审人员直观理解本方案的数值语义，下面给出与生产转换脚本 vllm_scripts/tools/convert_glm_int8_ue8m0.py[17] 完全一致的极简参考实现（包含：① 离线块级 Int8 + UE8M0 3 候选 MSE 量化、② 与目标 NPU 逐比特等价的 BF16 反量化，以及③ 过渡期从官方 FP8 [128, 128] 还原至高精浮点时的非整除维度保护）：

Int8 + UE8M0 离线量化与推理反量化参考代码（已逐比特校验通过） Python · PyTorch 
import torch

def quantize_int8_ue8m0(w: torch.Tensor, block_n: int = 16, block_k: int = 16):
    """离线量化：将 BF16/FP32 权重 [N, K] 转为 (int8 [N, K], uint8 UE8M0 [N/bn, K/bk])"""
    n, k = w.shape
    nb, kb = n // block_n, k // block_k
    blocks = w.float().view(nb, block_n, kb, block_k).permute(0, 2, 1, 3).reshape(nb, kb, -1)

    # 1. 计算无裁剪上界指数 u_ceil (scale = 2^(u - 127))，钳位到 SIMD 安全区间 [1, 247]
    s_req = torch.maximum(blocks.amax(-1) / 127.0, -blocks.amin(-1) / 128.0)
    is_zero = s_req <= 0.0
    u_ceil = (torch.ceil(torch.log2(s_req.clamp(min=2.0**-126))).to(torch.int32) + 127).clamp(1, 247)

    # 2. 离线 3 候选 MSE 优选：{u_ceil, u_ceil - 1, u_ceil - 2} 择块 L2 重建误差最小解（零推理开销）
    ones = torch.ones_like(u_ceil, dtype=torch.float32)
    best_err = torch.full((nb, kb), float("inf"), device=w.device)
    best_u, best_q = u_ceil.clone(), torch.zeros_like(blocks, dtype=torch.int8)
    for shift in (0, 1, 2):
        u_cand = (u_ceil - shift).clamp(min=1)
        s_cand = torch.ldexp(ones, u_cand - 127).unsqueeze(-1)
        q_cand = torch.round(blocks / s_cand).clamp(-128.0, 127.0)
        err = (q_cand * s_cand - blocks).square().sum(dim=-1)
        better = err < best_err
        best_err = torch.where(better, err, best_err)
        best_u = torch.where(better, u_cand, best_u)
        best_q = torch.where(better.unsqueeze(-1), q_cand.to(torch.int8), best_q)

    # 全零块统一置 u = 127 (即 2^0 = 1.0)，还原 [N, K] 布局
    best_u = torch.where(is_zero, torch.full_like(best_u, 127), best_u)
    best_q = torch.where(is_zero.unsqueeze(-1), torch.zeros_like(best_q), best_q)
    w_int8 = best_q.view(nb, kb, block_n, block_k).permute(0, 2, 1, 3).reshape(n, k).contiguous()
    return w_int8, best_u.to(torch.uint8).contiguous()


def dequantize_int8_ue8m0_to_bf16(w_int8: torch.Tensor, scale_u8: torch.Tensor,
                                  block_n: int = 16, block_k: int = 16) -> torch.Tensor:
    """推理反量化：与目标 NPU `cvt.bf16.s16 + fmul.bf16(u << 7)` 逐比特 100% 等价"""
    n, k = w_int8.shape
    nb, kb = n // block_n, k // block_k
    # UE8M0 字节 u ∈ [1, 254] 左移 7 位直接拼成合法 BF16 缩放因子 2^(u - 127)
    scale_bf16 = (scale_u8.to(torch.int32) << 7).to(torch.uint16).view(torch.bfloat16)
    # 任意 int8 转 BF16 零舍入，乘纯 2 的幂次 scale_bf16 亦零舍入，直接供 BF16 矩阵核全 K 连续累加
    w_bf16 = w_int8.to(torch.bfloat16).view(nb, block_n, kb, block_k)
    return (w_bf16 * scale_bf16.view(nb, 1, kb, 1)).reshape(n, k)


def dequantize_official_fp8_block(w_fp8: torch.Tensor, scale_f32: torch.Tensor,
                                  src_block_size: tuple[int, int] = (128, 128)) -> torch.Tensor:
    """过渡路径前置步骤：从官方 FP8 [128,128] 还原高精浮点（必须显式传块尺寸防 576 非整除错位）"""
    n, k = w_fp8.shape
    bn, bk = src_block_size
    s_full = scale_f32.float().repeat_interleave(bn, dim=0).repeat_interleave(bk, dim=1)[:n, :k]
    return w_fp8.float() * s_full  # 随后直接送入 quantize_int8_ue8m0(..., 16, 16)

5.1.2 真实目标 NPU 四步全 Shuffle SIMD 反量化流水线与实测收益

上述反量化代码之所以能在硬件上跑到极致，是因为前期设计参考[18]从数学上证明了全部 256 × 256 = 65,536 种 (int8, ue8m0) 组合在 BF16 中均为 100% 精确无舍入值（彻底省去 int8 → int32 → fp32 → mul → rne_bf16 的 4 倍拆包与舍入开销）。目前在真实目标 NPU 上已确认落地最优的「四步全 Shuffle 极速转换方案」（对应选型指南最高优先级路线 1b 变体）：

  1. 全 Shuffle 选择装入每 16-bit 通道高 8-bit：一步把紧凑排列的 int8 字节直接放入各 16-bit 向量通道高字节（bits [15:8]），省去传统多级 unpack 指令；
  2. 算术右移 8 位（sra.s16 #8）：单条定长算术右移同时完成归位与 int8 → int16 带符号位扩展；
  3. 硬件原生整型转 BF16（cvt.bf16.s16）：全程保持 16-bit 满宽通道（吞吐为 FP32 路径的 2×），无分支、无 clz、无 0 / -128 特判；
  4. 原生 BF16 乘折入缩放（fmul.bf16）：循环外准备一次 v_sc = vdup(uint16(u) << 7)，内层单条 fmul.bf16 即把块缩放直接折入权重 BF16 指数（硬件无分支精确覆盖 scale ∈ [1, 254]；离线量化脚本主动钳位在 [1, 247] 以兼顾所有五级 SIMD 路线），随后 BF16 矩阵核可沿完整 K 维连续累加，彻底免去每块出栈乘 FP32 scale 的累加器中断开销。

6 分阶段推进路线、跨团队协作诉求与风险对策

图 8：Int8 + UE8M0 离线量化三阶段工程推进路线图

给矩阵乘算子团队的配合诉求

  • 交付优先级：按参数占比与耗时收益依次交付 MoeGroupedGemmWithIndex (w13) → MoeGroupedGemm (w2) → Int8Linear → int8_block_dequant。
  • 统一算子契约：消费标准补码 int8 + uint8 UE8M0，参数化支持 [16,16] 与 [32,32]；采用“反量化预折入 BF16 指数 + 全 K 维连续累加”，结合各后端私有 Prepack 优化片上 DMA 搬运。
  • 自动化验收单测：复用仓库 torch_xcpu/test/ops/test_int8_ue8m0_16x16.py 完成全量 65,536 组合逐比特对拍及融合 SiluAndMul 单测[17]。

给管理层的决策要点与风险控制

  • 立项投入产出比：仅需一套统一 Int8 + UE8M0 算子栈，换取实测 3.5×~4.7× 反量化加速、极低单卡显存增量（DP16×TP4×EP64 理论估算仅 +67.3 MB / +0.333%，以实际部署为准）、跨模型算子复用以及向未来硬件原生 W8A8 的平滑演进能力。
  • 风险 1（端到端跑分尚未闭环）：Phase 1 控变量验证后，Phase 2 立即执行全量 Benchmark 跑分把关；待 GLM-5.3-BF16 源权重导入后切换为 BF16 直转（算子精度全面反超官方 FP8）。
  • 风险 2（FP8 二次转码敏感层）：转换工具已固化保留 indexer.wk（17 MB），避免稀疏注意力召回退化。
