# 20261118 更新说明（20261116 至 20261118）

注意！

- **`vllm`、`vllm-xcpu-plugin` 与 `torch_xcpu` 需配套升级**：
  - **GLM-5.2 / DeepSeek-V3.2 Sparse MLA INT8（UE8M0, group=32）KV Cache 跨三仓协同落地**：、
    - 更新 GLM 相关 preset，并在启动时设置在环境变量 `USER_VLLM_KV_CACHE_DTYPE=int8` 生效
    - 建议清理旧 `vllm_cache`。
    - `torch_xcpu` `eada826` 在 6 个 DS-MLA 算子（`sparse_mla_fp8`、`sparse_mla_fp8_vproj`、`reshape_and_cache_mla_fp8_ds`、`unified_attention_mla_fp8_ds`、`fused_mla_rope_cache`、`fused_mla_rope_qproj_cat_cache`）的 Torch schema 末尾追加 `int quant_mode=0`（`0=fp8_ds_mla`、`1=int8_ds_mla`，保持 656 B/token 页条目布局不变）并为 `SparseMlaFp8` 新增 `kv_cache_dtype` 参数；
  - **GDN Chunk/Cache 机制升级**：支持非 PageSize 对齐的 GDN checkpoint 并改善其 Cache 机制，具体见后
  - **DSpark 融合采样、融合拒绝采样与 MoE EP `topk=3` / 多布局窗口配套依赖**：支持 TopK=3 的 MoE，让同一个模型中，不同部分 TopK 不同的 MoE 共享同一块接收缓冲区
- **DSpark Markov 采样融合与量化运行参数说明**：
  - 插件默认开启融合（`VLLM_XCPU_DSPARK_MARKOV_FUSED=1`）与 BF16 权重（`VLLM_XCPU_DSPARK_MARKOV_DTYPE=bf16`）；可设 `VLLM_XCPU_DSPARK_MARKOV_DTYPE=fp8|int8` 启用加载期 `[32, 32]` OCP UE8M0 在线量化与重排（自动释放 `markov_w2._xcpu_bf16_linear` 省回约 63.1 MiB 内存），或设 `VLLM_XCPU_DSPARK_MARKOV_FUSED=0` 手动回退逐算子循环。
  - `torch_xcpu` 中 `TORCH_XCPU_DSPARK_MARKOV_SAMPLE{,_FP8,_INT8}_IMPL` 默认走 `A0`（OpenMP 单并行区融合，兼容 DeepSeek-V4.1 x86 下 32/64 线程约束）；x86 模拟 `A1`（96-PE Mega-Kernel）需 `OMP_NUM_THREADS >= 96`，**建议目标 NPU 平台参考 `A1` 实现 Mega-Kernel 版本并设为默认**（详见 `torch_xcpu/docs/deepseek_v41/dspark_markov_sample.md`）。
- **P/D 分离下 DFlash / DSpark 配置更新（`prefill_context_kv_only` 与批次预算对齐）**：
  - 合入 `vllm` `26eb61180a`（`#59468`）与 `5376027ec5`（`#54163`）后，Prefill 实例无需再将 `max_num_batched_tokens` 设为 `6144 + K = 6149` 凑整，P 与 D 统一设为 `6144` 即可满预算对齐切分。
  - Prefill 实例推荐在 `--speculative-config` 中开启 `"prefill_context_kv_only": true`（如 `{"model":"z-lab/Qwen3.8-27B-DFlash2","num_speculative_tokens":5,"method":"dflash","prefill_context_kv_only":true}`）：P 侧保持与 D 完全一致的 KV Cache Group 布局（通过 Mooncake 正常传输目标层 KV/GDN 状态与 drafter context KV），跳过首次无用 `propose` 与 draft attention metadata 构建，并在加载后自动释放非 context KV 所需的 draft 权重（`Qwen3.8-27B-FP8` + `DFlash2` 在 `TP=2` 下每 rank 释放 `2.00 GiB` 参数，实测单 rank 权重与非 Torch 占用从 `17.88 GiB` 降至 `15.75 GiB`）。

## 更新重点

- **DSpark 投机解码全链路优化（上下文投影堆叠、SP 延迟聚合、5 步 Markov 融合采样 + FP8/INT8 UE8M0 跨步 SRAM 常驻、融合拒绝采样）**：
  - **插件端上下文投影与 SP 延迟聚合（`c8f75f5`、`9880fdf`）**：`XcpuDSparkDeepseekV41Model` 在量化/BF16 打包前暂存各层对齐的 `wkv` 切片，加载完成后堆叠为单个 `torch_xcpu` FP8/BF16 linear 并释放临时缓存；Greedy 采样路由至 `torch_xcpu.ops.argmax_out`，同步刷新提前导入的 `gumbel_sample` 绑定；运行时空闲 DP 同步步（`torch_xcpu.ops.is_dummy_run()`）短路 `combine_hidden_states`、无槽位 `precompute_and_store_context_kv` 与顺序采样；开启 SP 且 `PP=PCP=1` 时推迟 Target 各 aux 层的 SP all-gather，将分片打包进持久缓冲返回 `SpShardedAuxHiddenStates`，在 DSpark 侧先于 TP 分片执行 `combine_hidden_states` 再做单次 `all_gather_into_tensor_out_v2`。
  - **5 步 Markov 采样融合与低精度跨步 SRAM 常驻（`torch_xcpu` `33997ac`、`06fb7ea`、`28da327` + 插件 `0d27bdc`、`6e8dfdc`）**：新增 `dspark_markov_sample`（BF16）及 `dspark_markov_sample_fp8` / `dspark_markov_sample_int8`（`[32, 32]` OCP UE8M0 块缩放），将 5 步 × 5 算子 = 25 次串行 launch 收敛为 1 次 launch，词表按列分块在片上完成 `markov_w1` 查表、`markov_w2` 投影、`base_logits` 叠加及 Greedy/Gumbel-Max 归约（支持 `weight_layout=0/1/2`、可选 `draft_logits` 写出、`markov_embeds_out` 收集及 Greedy `d2t` 映射）。同时提供 `A0`（默认 OpenMP 融合，支持 AMX `intel_amx_bf16_tile32`）与 `A1`（96-PE Mega-Kernel：低优先级双缓冲 DMA、Sub-Die RMA 两级归约将 HBM 工作区从 24 KiB 降至 512 B、双 leader 冗余归约省去第 2 次全局 `barrier()`；FP8/INT8 版启用 20 槽跨步 SRAM 权重常驻 + 尾块双缓冲，在预留 >= 32 KiB NPU SRAM 余量下使 $V=129280$ 的 85.5% 权重仅 Step 0 读一次 HBM，5 步 `markov_w2` HBM 读取从 157.97 MiB 降至 49.86 MiB，配套扩展 `mk::kernels::{VecAdd,BlockArgmax,BlockGumbelMax,Gemm}` 的 UE8M0 支持）。
  - **融合投机拒绝采样（`torch_xcpu` `33997ac` + 插件 `0d27bdc`）**：新增 `vllm_rejection_sample_fused` 并在插件重绑 `RejectionSampler._verify`——当仅启用温度缩放（无 top-k/top-p/min-p/penalties/logit_bias/bad_words/thinking_budget/watermark/block verification）时跳过 `apply_sampling_params` 的全词表 FP32 拷贝与独立温度 kernel，在单次 launch 内完成在线温度缩放、LSE、逐拍接受判定与拒绝残差重采样。

- **vLLM 核心投机解码（DFlash/DSpark）与混合 Mamba/GDN 调度及 KV Cache 优化回移（`vllm` `c2a463cf28`、`26eb61180a`、`5376027ec5`、`ac93f4d59c`、`a769d3b9c4`、`db3be6876c` + 插件 `29f80e4`）**：
  - **调度预算与末尾前缀块修复（`26eb61180a`、`5376027ec5`）**：`#59468` 取消在目标模型调度预算中预扣 DFlash/DSpark draft 槽位（仅按 `max_num_batched_tokens // num_lookahead_tokens` 约束最大并发活跃序列数），消除混合 Mamba `align` 模式下因 `6144 - 5 = 6139` 向下整块取整损失一整块吞吐的问题；`#54163` 令 `use_eagle_block_drop()` 对 DFlash/DSpark 返回 `False`（context KV 仅依赖当前位置 target hidden state），避免 `last_cache_position` 多退一整块导致的额外切分与命中重算。在 `8192` 输入（`N = 6144, K = 5`）下，`--block-size 256`（`B = 1024`）由 3 轮 `5120 / 2048 / 1024` 收敛为 **2 轮 `6144 / 2048`**；`--block-size 128`（`B = 896`）由 `5376 / 1792 / 1024` 恢复为 `5376 / 2688 / 128`，命中回放/续写重算量从 `1024` 降至 **`128` tokens（减少 87.5%）**。

切分与命中边界关键细节（基于 `vllm` `KVCacheManager` 与 `Scheduler._mamba_block_aligned_split` 源码验证）：

- **为何 `--block-size 256`（`B = 1024`）必须同时合入 `#59468` 与 `#54163` 才能 `2` 轮完成 `8192` Prefill**：`#59468` 让首轮吞吐不再卡在 `floor(6139 / 1024) * 1024 = 5120` 而跑满 `6144`；`#54163` 取消末尾退块后，`last_cache_position` 由 `8192 - 1024 = 7168` 恢复到 `8192`（`_mamba_block_aligned_split` 仅在 `start < stop < end` 严格位于区间内部时截断），从而避免第 2 轮 `6144 -> 8192` 在 `7168` 处被二次拆分为 `1024 / 1024`。
- **精确整倍数 `L = 8192` 在 `B = 1024` 默认稀疏保留（`prefix_cache_retention_interval = 0`）下的边界说明**：当 `num_prompt_tokens` 严格为 `8192`（不含 chat template 等额外 token）时，`get_replay_boundaries` 按 `L - 1 = 8191` 计算唯一回放边界（落在 block 6 末尾 `7168`），而第 2 轮 `6144 -> 8192` 单步跨过 block 6 与 block 7 仅在块尾 `8192`（block 7）写出 GDN 状态，导致该精确边界下 block 7 不被默认稀疏掩码保留；而在实际对话场景经 chat template 包装（例如 `L = 8208`）后，`L - 1 = 8207` 使 block 7（`8192`）正落于回放边界，回放与续写均直接命中 `8192`。

### 3. Cache 与设备内存节省测算（Qwen3.8-27B-FP8 + DFlash2, TP=2）
