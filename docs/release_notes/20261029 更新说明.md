## 更新重点

- **加速器释放 / 重载（sleep / wake_up）**：上层路由可以通过 `POST /sleep`、`POST /wake_up` 让 vLLM 实例释放并重新获取加速器运行时，用于查验、借用等场景。vLLM 本身不会自动 sleep 或唤醒，两者只由这两个 HTTP 调用触发。设备内存全程原位有效，权重、KV cache 和运行时缓冲不卸载。torch_xcpu 新增 `device_runtime_sleep` / `device_runtime_wake_up` 接口，x86 为空实现，**NPU 团队需要在 `torch_xcpu_impl/src/device_runtime.cpp` 中实现**。使用方法见下文「加速器释放 / 重载使用说明」。
- **启动时预留 KV cache 设备内存**：`VLLM_XCPU_RESERVE_KV_CACHE`（默认 1，设为 0 关闭）。在 `init_device` 设备堆还是空的时候占住 `VLLM_CPU_KVCACHE_SPACE` 大小的内存，加载权重和 profile 之后再交给 KV cache 分配，避免显存小的 NPU 上因堆碎片导致 KV cache 整块分配失败。共享 KV cache 模式不受影响。
- **PyTorch：cpp_wrapper 的 C++ 快速入口与静态输入借用**（新增 PyTorch patch）：JIT cpp_wrapper 图原先每次调用由 Python 逐个转换全部输入（大模型图约千个输入，提交说明记录约 1 ms host 耗时）。现在默认由 `torch._C._aoti.InductorEntry` 在 C++ 中完成转换，参数、buffer 等静态输入以借用方式传入图并跨调用复用 handle。提交说明记录的 Qwen3.8-27B-FP8 TP2 DFlash2 spec decode 每步 compiled graph 调用 host 耗时：bs=1 由 7.76 ms 降到 6.19 ms，bs≥8 由 8.01 ms 降到 5.80 ms（与 `TORCHINDUCTOR_CPP_WRAPPER_FAST_ENTRY=0` 的交替对照）。同时修复 AOT autograd 在去重参数或合成 base 时丢失 `static_input_indices` 的问题。**需要重新编译 PyTorch**，见下文「PyTorch patch」。
- **GDN metadata 跨 Mamba group 复用**：插件接入 vLLM MRV2 的 metadata 复用（每个 Mamba spec 只构建一次，其他 group 用 `update_block_table` 重新 gather）。新增 `torch_xcpu::mamba_aligned_state_indices` 算子。**需要配套本次的 vLLM patch**。
- **DFlash host 耗时优化**：`_C::rms_norm` 改走 torch_xcpu 的 C++ 注册，grouped cache 更新的几何检查按缓存复用。提交说明数据：27B spec-decode 每步 rms_norm 由约 195 µs 降到约 50 µs，grouped-update 检查由约 138 µs 降到约 77 µs。
- **`aten::index` 接受 CPU 索引**：行为对齐 CUDA 的 `expandTensors(ensure_same_device=true)`，CPU 掩码在 host 上展开，CPU 索引经 pinned 快照拷贝到设备，host 不等待 stream。
- **MoE EP v5 route 可不依赖 dispatch recvcounts**：新增编译宏 `XCPU_EP_V5_ROUTE_WITHOUT_RECVCOUNTS`（默认 0）。无论宏取值，dispatch window 创建时都填 `0xFF`，route 消费 header 后都会把 `rows` 写回 `-1`（见下文算子变更）。
- **torch_mcpu 越界防护**：`vllm_post_update` 对越界请求下标、总长度和 token id 做保护；`mcpu::vllm_rejection` 新增末尾参数 `vocab_size`，词表范围外的 draft token 不再被接受。插件已同步传入该参数（`ef21c71`），torch_mcpu 与插件两个源码包可以组合使用。
- **P/D 分离支持 P 与 D 使用不同 preset**：`pd_launcher.sh` 新增 `USER_VLLM_PD_PREFILL_PRESET` / `USER_VLLM_PD_DECODE_PRESET`，可为 P、D 角色分别指定 preset（例如 P 的 `max_num_batched_tokens` 多留出 draft slot）。两边的 KV 布局必须一致，**包括 speculative config**：P 不带 drafter 而 D 带 DFlash 会在 Mooncake 对齐 KV 区域时报 `registered group index mismatch`。详见 `docs/dev_log/20261029_Qwen3.8-DFlash2-PD-prefill-chunk.md`。

## 加速器释放 / 重载（sleep / wake_up）使用说明

### 工作方式

上层路由要求某个实例释放加速器时，调用 `/sleep`。实例暂停调度、清空 prefix cache，并在每个 rank 上调用 `torch_xcpu.device_runtime_sleep`，释放计算上下文（PE 团队、stream、驱动句柄等）。此时 NPU 可以被其他任务查验或借用。归还后调用 `/wake_up`，每个 rank 调用 `torch_xcpu.device_runtime_wake_up` 重新获取，全部成功后恢复调度。

设备内存全程原位有效：权重、KV cache、运行时缓冲都不卸载，设备指针不变，所以 compile 产物和已缓存的指针无需重建。这依赖一个前提：NPU 驱动在释放计算上下文后仍保持设备内存映射和内容。若驱动把设备内存绑定在 context 生命周期上，该前提不成立，需要改用「卸载权重、丢弃 KV、唤醒后重建」的方案，请 NPU 团队尽早确认。

### 启用

启动参数需要 `--enable-sleep-mode`，并设置环境变量 `VLLM_SERVER_DEV_MODE=1`（`/sleep`、`/wake_up`、`/is_sleeping` 位于 vLLM 的 dev 路由下）。平台会自动把默认的 `cumem` 后端换成 `xcpu`，不需要额外参数。在预设中加入：

```bash
export VLLM_SERVER_DEV_MODE=1
_VLLM_OPTIONAL_ARGS+=" --enable-sleep-mode"
export VLLM_OPTIONAL_ARGS="${_VLLM_OPTIONAL_ARGS}"
```

完整示例见 `vllm_scripts/presets/serial/Qwen3-0.6B_dp1_tp1_eager_sleep.sh`。

`VLLM_SERVER_DEV_MODE=1` 会同时开放 `/collective_rpc` 等一批开发端点，可在 worker 上调用任意方法。服务只应暴露给内网的路由，不要对外开放。

### 接口

| 动作 | 请求 | 成功响应 |
| --- | --- | --- |
| 释放加速器 | `POST /sleep?level=1&mode=wait` | `{"status": "sleeping", "level": 1}` |
| 重新加载 | `POST /wake_up` | `{"status": "awake", "tags": null}` |
| 查询状态 | `GET /is_sleeping` | `{"is_sleeping": true}` |

```bash
curl -X POST "http://127.0.0.1:${PORT}/sleep?level=1&mode=wait"
curl "http://127.0.0.1:${PORT}/is_sleeping"
curl -X POST "http://127.0.0.1:${PORT}/wake_up"
```

- `level`：`0` 只暂停调度并同步设备，不调用 torch_xcpu，也不释放加速器，适合只要求设备静止的查验。`1` 和 `2` 在 xcpu 上行为相同，都会调用 `device_runtime_sleep(level)`，level 值原样传给 NPU 实现。路由方建议统一使用 `1`。
- `mode`：`wait` 等在途请求结束后再释放，`abort` 立即中止在途请求。以 HTTP 响应返回作为「已释放」的信号。
- `/wake_up` 不带参数即可。带 `tags` 的分批唤醒在 xcpu 上第一次就会重新获取整个运行时，但调度要等所有 tag 都唤醒后才恢复，路由方不需要使用。
- `release_kv_cache_memory` 在 xcpu 上不支持，调用会报错。

### 语义保证

以下语义按 vLLM 0.31 代码核对得出，除端到端测试覆盖的 sleep / wake_up / is_sleeping 往返外，没有做专项测试。

- vLLM 不会自动 sleep，也不会自动唤醒。引擎代码中没有空闲计时器或定时回调会在 sleep 期间调用设备；`/health` 只检查引擎进程是否存活，worker 的健康检查是空函数。
- sleep 期间到达的请求会进入等待队列，不会执行、不会触发唤醒、不会报错，直到 `/wake_up`。路由方承诺不路由请求，这只是兜底。
- `/sleep` 和 `/wake_up` 都幂等，重复调用只打 warning。
- `/wake_up` 中 `device_runtime_wake_up` 抛异常时（例如加速器仍被他用），接口返回 HTTP 500，实例保持 sleep 状态，可以稍后重试。torch_xcpu 层在异常时保持 sleeping 状态。该路径目前只做了代码分析，没有故障注入测试。
- DP 大于 1 时，`level=0` 不设置 sleeping 标记，本 rank 仍会为其他 rank 执行 dummy batch。需要设备静止时使用 `level=1`。

### 验证

```bash
# torch_xcpu 状态机
cd torch_xcpu && python -m pytest test/test_device_runtime_sleep.py -v
# 插件后端
cd vllm-xcpu-plugin && python -m pytest tests/plugin_tests/test_sleep_mode.py -v
# 端到端：greedy 输出 → sleep → wake_up → 同一 prompt 输出逐 token 一致，循环两轮
cd vllm_scripts && ./run_vllm_test.sh -e presets/serial/Qwen3-0.6B_dp1_tp1_eager_sleep.sh --sleep-test
```

x86 模拟器上两个钩子是空实现，端到端日志中 sleep 和 wake_up 各约几毫秒，只反映管道开销。真实耗时取决于 NPU 实现。

### NPU 团队需要实现的接口

位置：`torch_xcpu_impl/include/device_runtime.h` 声明，`torch_xcpu_impl/src/device_runtime.cpp` 实现（当前为 x86 空实现）。

- `xcpu_impl::device_runtime_sleep(int64_t level)`：在所有 stream 同步完成后调用。可以释放计算上下文，**不得释放或搬移设备内存**，进程持有的每个设备指针在唤醒后必须仍然映射且内容不变。
- `xcpu_impl::device_runtime_wake_up()`：恢复上一次 sleep 释放的全部资源，之后内核可在同样的 stream、同样的指针上继续运行。
- 两者进程级，每个 rank 各调用一次。状态记录、互斥、重复调用拒绝都在 torch_xcpu 层完成，实现不需要自己记状态。
- 失败以异常上报。唤醒失败时设备必须保持完全释放，以便稍后重试。

设计说明见 `docs/accelerator-sleep-wake.md`。

## torch_xcpu 算子变更

范围：`aaaf7362b57c04d1f5df44eb5c3dbf9486b3e07f`（不含，20261027 发布）至 `2a6dc82448ad44e57b27277ccb648d60cdb80b56`（含），共 5 个提交，全部为 dev/0.31 自身提交。

测试用于佐证行为，不代表覆盖了全部 shape、dtype、后端和并行组合。除 `device_runtime_sleep` 外，本次打包没有重新运行算子测试，结论取自各提交说明与文档。

### 影响 B0 算子实现

- `mamba_aligned_state_indices`（新增算子）：Torch schema 为 `mamba_aligned_state_indices(Tensor block_table_ptrs, Tensor seq_lens, Tensor(a!) state_indices, int block_table_stride_req, int num_reqs, int block_size) -> ()`，对应 vLLM MRV2 的对齐 state index 预计算。对每个 Mamba group `g`、请求 `r < num_reqs`、state 槽位 `s`：`state_indices[g, r, s] = block_table_g[r, max(0, (seq_lens[r] - 1) / block_size) + s]`。
  - 契约：`block_table_ptrs` 是连续的 int64 向量，每个元素是对应 group 的 int32 block table 在设备上的基地址；`seq_lens` 是 int32 向量；`state_indices` 是 int32 的 `[groups, reqs, slots]`，三维 stride 均由参数传入，不要求连续；`num_reqs == 0` 或输出为空时直接返回。
  - 版本选择环境变量为 `TORCH_XCPU_MAMBA_ALIGNED_STATE_INDICES_IMPL`，默认 A0。**B0 分支目前是占位**：选择 B0 时调用会抛出 `Unsupported mamba_aligned_state_indices implementation`，需要 B0 实现同一计算。
  - commit `e018d8d39ed09c18c3b2a99cd8ad77fc7cedbd81`：[GDN] add mamba_aligned_state_indices and derive GDN core slots on demand
  - 测试：`torch_xcpu/test/ops/custom_ops/test_mamba_aligned_state_indices.py`（与参考实现比较，覆盖 0、1、6 个请求，block size 1、4、64，带 stride 的输出，以及参数错误）。
- `fused_ep_moe_v5`（中等修改，route 阶段与 dispatch window 协议）：消息是否存在改由接收区 header 的 `rows` 自描述，`rows == -1`（`kMoeEpV5NoMessage`）表示该 region 没有消息，`0 <= rows <= C` 为有消息，`rows > C` 为非法。header 线格式的字段未变，变的是语义和读写时机。**B0 需要跟进**：
  - dispatch window 创建时必须整体填 `0xFF`，使每个 region 初始读作无消息。不能填 0，否则会读成「有消息、N = 0」。
  - route 在读完某个 header 的 `N` 和 `expert_count` 之后，必须把 `rows` 写回 `-1`（退役），再让这个 region 被后续 dispatch 重写。因此 dispatch window 不再是 route 的只读输入。
  - 分块调用（`has_next_round` 非空）中每个源每轮都必须发送 header，header 缺失（`rows == -1`）按非法处理。
  - 宏 `XCPU_EP_V5_ROUTE_WITHOUT_RECVCOUNTS`（编译期，默认 0，`fused_ep_moe_v5.cpp`）为 1 时，`MoeEpV5RecvState::recv_bytes_per_src_rank` 为 `nullptr`，route 只靠 header 判断。此时无法再用字节数校验长度，传输层必须保证 collective 返回时消息已完整可见，并只向所属的 dispatch 投递。宏为 0 时 route 仍读取 recvcounts，并与 header 交叉校验：计数为 0 必须对应无消息，非 0 必须对应有消息且长度恰为 `message_bytes(rows)`。
  - `MPI_Alltoall` + `MPI_Alltoallv` 仍作为一个整体，代表将来被替换的单一传输算子，其 recvcounts 数组现在只喂给这个替身。
  - commit `ce8436853ef160b4bb2e25b981992a4323057ea4`：[MoE] fused_ep_moe_v5: route without dispatch recvcounts behind a macro
  - 测试：`torch_xcpu/test/ops/custom_ops/test_moe_ep_v5.py`（新增无 recvcounts 的 route、全 `0xFF` 与带残留正文的窗口、空源、分块缺 header、route 退役 header）。`torch_xcpu/docs/moe_ep_v5.md` 末节记录了 2026-10-29 在 x86 release 构建上宏为 0 与 1 的验证范围；未运行 `XCPU_EP_V5_COMPILE=1`、端到端 vLLM 模型和真实 NPU。
- `device_runtime_sleep` / `device_runtime_wake_up`（新增运行时接口，非算子）：见上文「NPU 团队需要实现的接口」。x86 为空实现，**B0 需要提供真实实现**，否则 `/sleep` 不会真正释放加速器。torch_xcpu 层负责状态与互斥，未初始化时拒绝 sleep，重复 sleep 或未 sleep 即唤醒都会抛错，唤醒抛异常时保持 sleeping 状态。
  - commit `2a6dc82448ad44e57b27277ccb648d60cdb80b56`：[Runtime] add device_runtime_sleep/wake_up hooks for vLLM sleep mode
  - 测试：`torch_xcpu/test/test_device_runtime_sleep.py`（初始化检查、状态机、sleep 前后同一设备指针上的计算结果一致）。

### 不影响 B0 算子实现

- `build_gdn_metadata` / `gdn_core_tensors`（中等修改，Python 绑定契约变化）：`torch_xcpu._C.build_gdn_metadata` 返回的 `tensors` 不再包含 11 个 core graph-input 槽位，这些槽位改由新增的 `torch_xcpu._C.gdn_core_tensors(sources)` 根据 metadata 字段按需派生，因此 `dataclasses.replace()` 复制出的 metadata 得到与自身 state index 一致的槽位。`gdn_core_tensors` 接收 11 个可选张量，缺失的字段用空张量占位（dtype 按槽位固定），至少需要一个字段存在。直接使用旧返回值的调用方需要改为调用 `gdn_core_tensors`，插件已同步。`torch_xcpu_impl` 中的 GDN launch impl 和参数结构未改，无需修改 B0。
  - commit `e018d8d39ed09c18c3b2a99cd8ad77fc7cedbd81`：[GDN] add mamba_aligned_state_indices and derive GDN core slots on demand
  - 测试：torch_xcpu 内没有 `gdn_core_tensors` 的专项测试；覆盖在插件的 `tests/plugin_tests/test_gdn_patch.py` 和 `tests/layers/test_gdn_core_state.py`。
- `index`（`aten::index.Tensor`，中等修改，host 侧）：CPU 布尔或字节掩码在 host 上用 `nonzero()` 展开为各维的 long 索引，每个 CPU 索引先拷到新的 pinned 缓冲再以 `non_blocking` 拷到 `self` 所在设备，host 不等待 stream，调用方之后的写入也不会影响已入队的 launch。形状由展开后的 long 索引推出，不读设备。1-D CPU 掩码现在走 dim0 `index_select` 快速路径。设备索引原样透传。下游 launch impl 和参数未改，无需修改 B0，B0 只需注意这条路径会产生额外的小块 H2D 拷贝。
  - commit `6bd2a5926234c2c93aab780179cf64a1f338f302`：[ATen] accept CPU indices in aten::index the way CUDA does
  - 测试：`torch_xcpu/test/ops/aten/test_index.py`、`torch_xcpu/test/ops/aten/test_index_impl.py`。
- `rms_norm`（新增 C++ 注册入口，host 侧）：`register_vllm_rms_norm()` 为 vLLM 的 `_C::rms_norm(Tensor! out, Tensor input, Tensor? weight, float epsilon)` 注册 PrivateUse1 boxed kernel，检查与慢路径（跨步 packing、FP16 与未对齐 BF16 升到 FP32、输出与输入或权重别名时先写临时张量）与插件的 Python kernel 一致，并在 `_C::rms_norm` schema 不符合预期时拒绝注册。底层仍调用原有的 `rms_norm_cpu` launch，没有改动 `torch_xcpu_impl`，无需修改 B0。提交说明记录的 host 耗时由约 32 µs 降到约 9 µs，输出逐位一致。
  - commit `1c044d172ce10182e302546fa103d0af78c56420`：[DFlash] add a C++ PrivateUse1 kernel for vLLM's _C::rms_norm
  - 测试：torch_xcpu 内没有专项测试；插件的 `tests/plugin_tests/test_rms_norm_dispatch.py` 校验 C++ 与 Python 两种实现逐位一致。
