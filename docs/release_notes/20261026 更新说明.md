# 20261026 更新说明（20261014 至 20261026）

## 更新重点

- GLM5.2 在 0.31 上完成适配
- GLM5.2 共享 KV cache
- 恢复实现 Qwen3.5/3.6 GDN 输入投影融合
- torch_mcpu stream host cpu 开销降低
- 构建 **异步 Spawn** 初步基础设施，目前适用于 fused_moe_v5 中的 shared expert 计算等

---

- **合入 dev/0.25（至 0.25 的 20261019 版本）**：torch_mcpu、torch_xcpu、vllm-xcpu-plugin、vllm-xcpu-dev-kit 各做了一次 `Merge branch 'dev/0.25' into dev/0.31`。带入的 torch_mcpu `aten::minimum`/`minimum.out`、`fused_ep_moe_v5` 重写（固定 region、dispatch/combine 双窗口、`fused_ep_moe_v5_initialize_windows`）、shared expert 融合、`moe_grouped_gemm_with_index`/`indexed_gather`、EP/AF 字节重叠检查、Inductor 中间 buffer 内存池默认开启、TRACE_ONCE 全量 trace、DSA prefill buffer 上限等内容，已在 0.25 的 `20261019 更新说明.md` 中描述，本文不再重复，只写 merge 及其后的增量。
- **merge 增量（20261019 之后 dev/0.25 的新提交，随本次 merge 首次交付）**：
  - MoE 序列并行跳过 padding 行（vLLM `0670c36056` + torch_xcpu `de3b6a1` + 插件 `8ca8a0c`）：在 SP MoE 之前，norm 直接写出本 rank 的 SP chunk，不再调用 `constant_pad_2d`；`fused_ep_moe_v5/v6` 允许 `topk_ids` 只覆盖前 `num_valid_tokens` 行，padding 行不分发、不跑融合 shared expert，输出写零。新增 `fused_add_rms_norm_chunk_out`，`moe_finalize_hybrid_reduce_v5_v8` 新增 `num_valid_rows`。
  - 流式 kernel launch（torch_xcpu `97a0f7c`）：新增 `KernelJoinMode`。FP8/MXFP4 linear 新增 `*_out_with_join_mode` C++ 入口，`silu_and_mul` 带 join_mode 参数。阻塞 dispatch 模式下，`fused_ep_moe_v5` 把 shared MLP 改到 dispatch 之前、以 `Spawn`（不 join）方式提交，让它与 alltoallv 重叠。
- **GLM5.2 在 0.31 上完成适配**：
  - 插件把 GLM5.2 sparse MLA 迁到 `attention/` 下，删除 GLM5.2 之前的 dense MLA 路径（`mla_patch`、`flashattn_mla_sparse_patch`、TRITON_MLA 路由），indexer 只走 C++ core。
  - vLLM 新增 MXFP4 MoE backend 选择、sparse MLA cache dtype/wrapper class、shared-expert combine 三个 OOT hook。
  - SP 布局改为显式跟踪；compile 下用 XCPU 算子做 SP pad/chunk；新增 `VLLM_DISABLE_ATTN_REDUCE_SCATTER_FOR_MOE`；GLM draft config 保留 FP32 路由。
  - AFD 支持 GLM5.2 真实权重和 DFlash/DFlash2 草稿；未传 `--all2all-backend` 时 A/F 默认使用 V8。
- **GLM5.2 共享 KV cache**：
  - torch_mcpu 新增共享内存分配器 `xmalloc`。
  - 插件在 `VLLM_XCPU_SHARED_KV_CACHE=1`（默认 0）时，让本地 TP worker 共享 GLM5.2 的 MLA/indexer KV 存储，TP2 下存储降到 1/2；DFlash 草稿 cache 仍各自私有；共享 KV 暂时拒绝 PCP>1。
  - vLLM 新增 KV cache allocator hook，MRV2 PCP 放开 DFlash。
  - 插件放开 GLM sparse MLA 路径的 PCP 检查（DCP 仍须为 1）。
- **Qwen3.5/3.6 GDN 输入投影融合**：`VLLM_XCPU_FUSE_GDN_IN_PROJ_QKVZBA=1`（默认）时，无 LoRA 的 BF16 层把 qkvz 与 ba 合成一个 `in_proj_qkvzba` GEMM，每层少一次 GEMM，下游使用零拷贝 view。native core 同步改用共享投影。
- **torch_xcpu（dev/0.31 自身）**：
  - 删除最原始的朴素实现 `sparse_mla_prefill`/`sparse_mla_decode`
  - `sparse_attn_indexer` 与 vLLM 0.31 对齐：不规则 decode batch 走 padded 路径；weights 必须连续。
- **torch_mcpu**：
  - stream 优先级范围改为与 CUDA 一致的 (0, -1)；低优先级 stream 改用 hybrid idle，每次 launch 由 209 ns 降到 101 ns（基准测试数据）。
  - `gather_block_tables` 接受 int64 `idx_mapping`。
  - merge dev/0.25（`aten::minimum`/`minimum.out`，已在 20261019 描述），无增量。

模型支持情况：

- Qwen3.5/3.6/3.8 + DFlash/DFlash2：沿用 20261014 的支持状态，本次新增 GDN 输入投影融合。
- GLM5.2 FP8/MXFP4：各提交说明记录的验证覆盖串行 TP1 eager/compile、DP2/TP2 SP-MoE compile（dummy 权重）、AFD A1+F2（真实权重，含 DFlash2）、共享 KV TP2/TP4。MTP 仍被 XCPU sparse MLA 拒绝；DCP 不支持。

建议设置：

- `user_env` 随 merge 带入了 20261019 的默认值变化（Inductor 内存池等），请务必对照 `vllm_scripts/user_env_template.sh` 更新。GLM5.2 的 `USER_VLLM_MAX_NUM_SEQS`、EP64 的 `VLLM_XCPU_MOE_MAX_RECV_TOKENS` 建议同 20261019。
- GLM-5.2 compile 预设需设置 `VLLM_USE_BREAKABLE_CUDAGRAPH=0`：v0.31 会为 DSA 自动选择 breakable CUDA graph，而这会关闭 compile。v5 compile 预设已经加上这一设置。

## torch_xcpu 算子变更

范围：`23380c5211a49ce00751f89d2c0a80b08b1d4cde`（不含，2026-10-14 发布）至 `a38ae1f2cf8da5bcb771f0dcb9b8b4088611c7bc`（含）。包括 dev/0.31 自身的 `e2d368f`、`4700efa`，以及 merge 增量 `de3b6a1`、`97a0f7c`。merge 带入的 7 个已在 20261019 描述的提交不再重复，涉及 `moe_grouped_gemm_with_index`、`indexed_gather`、`moe_ep_v5_pack`/`route`/`local_reduce`、`moe_finalize_hybrid_reduce_v5_v8`（shared merge、`receive_rows_per_rank`）、`fused_ep_moe_v5` 重写，以及 `fused_ep_moe_v6`/`fused_af_*` 的字节重叠检查，请参阅 0.25 的 `20261019 更新说明.md`。

测试用于佐证行为，不代表覆盖了全部 shape、dtype、后端和并行组合。本次打包没有重新运行算子测试或端到端测试。

### 影响 B0 算子实现

- `fused_add_rms_norm`（中等修改）：参数结构 `fused_add_rms_norm_arg_t` 新增 `output_row_begin`（默认 0）和 `output_rows`（默认 -1，表示完整 `[num_tokens,H]` 输出）。
  - 新语义：`residual_out = input + residual` 仍覆盖全部 token 行；归一化结果只把 token 行 `[output_row_begin, output_row_begin+output_rows)` 写入 `output` 的 `[0, output_rows)` 行，窗口中超过 `num_tokens` 的行写零（SP padding）；窗口外的 token 不计算归一化，也不写 output。
  - B0 需要同步的内容：新参数、窗口外跳过、padding 行清零。A0 的 DMA 写回计数也随之改变，每个 token 写回 1 或 2 次，按 stage 记录已发出的写回数后再等待。原有 `fused_add_rms_norm_out` 传入 `(0,-1)`，行为不变。
  - 新增 Torch 入口 `fused_add_rms_norm_chunk_out_bf16/fp32(Tensor(a!) output, Tensor(b!) residual_out, Tensor input, Tensor residual, Tensor weight, float epsilon, SymInt row_begin) -> ()`，Python 端为 `torch_xcpu.ops.fused_add_rms_norm_chunk_out`。要求 input 为二维 `[T,H]`，output 为 `[rows,H]`，各张量末维连续、行不重叠，`row_begin>=0`。vLLM `sequence_parallel_add_rms_norm_chunk` 在 MCPU 上使用该入口。
  - commit `de3b6a151c3d0a4b6f605036278cd810cda9aa3b`：[MoE][SP] skip sequence-parallel padding rows in RMSNorm and fused EP MoE
  - 测试：`torch_xcpu/test/ops/custom_ops/test_fused_add_rms_norm.py::test_fused_add_rms_norm_chunk_out`（BF16/FP32，hidden 64/6144，多种 token 数与 TP 切分）。

- `moe_finalize_hybrid_reduce_v5_v8`（小修改）：`MoeFinalizeHybridReduceV5V8Args` 新增 `num_valid_rows`（默认 -1，表示全部有效）。
  - 行 `[num_valid_rows, num_input_rows)` 是 SP padding：不读 return indices、不累加、不读 shared 输出；finish 轮直接写零行，非 finish 轮跳过。
  - B0 需要同步新字段和 padding 行处理。`fused_ep_moe_v5`、`fused_ep_moe_v6` 会传入该字段；v7/v8 AF 路径不设置，保持默认值。
  - commit `de3b6a151c3d0a4b6f605036278cd810cda9aa3b`：[MoE][SP] skip sequence-parallel padding rows in RMSNorm and fused EP MoE
  - 测试：`torch_xcpu/test/mpi_custom_ops/test_fused_ep_moe_v5_mpi.py`（padding-row 用例，端到端覆盖）；未新增 finalize 的专项单测。

- `moe_prepare_hybrid_pack_v5_v8`（小修改，契约变化）：A0 kernel 代码未改，只更新了注释。但从本次起，`fused_ep_moe_v6` 在正常（非 dummy）运行中也会传入 `num_input_rows < original_num_input_rows`，即 SP padding 行，此前只有 dummy run 会出现 `num_input_rows=0`。
  - B0 需要确认：行 `[num_input_rows, original_num_input_rows)` 不参与打包，`return_row_indices` 置为无效值，`ids/weights` 只读前 `num_input_rows` 行。
  - commit `de3b6a151c3d0a4b6f605036278cd810cda9aa3b`：[MoE][SP] skip sequence-parallel padding rows in RMSNorm and fused EP MoE
  - 测试：未新增对应 v6 padding 行的专项测试（MPI padding-row 用例只覆盖 v5）。

- `fp8_linear`、`mxfp4_linear`（中等修改）：各后端的 `scaled_mm_wrapper` 末尾新增 `KernelJoinMode join_mode` 参数（`torch_xcpu_impl/include/kernel_join_mode.h`：`SpawnJoin=0` 为默认，`Spawn=1` 表示只 spawn、由后续 join 统一等待；`JoinSpawn=2`、`JoinSpawnJoin=3` 为预留值，未实现）。
  - Acc 后端（`AccFp8LinearKernel`、`AccMxfp4LinearKernel`）的 launch 体改为仅在 `SpawnJoin` 时调用 `xthd_join()`，源码标注了 `TODO(accelerator)`。B0/加速器实现需要支持 `Spawn`：返回时 PE 可以仍在运行，同一 stream 上的后续 launch 必须保持顺序，并由后续 join 等待。
  - Portable/PaddingExample/Intel AMX 后端只接收参数并忽略它（host kernel 不经 xthd spawn）。
  - 新增 C++ 入口 `fp8_scaled_mm_<Suffix>_out_with_join_mode`、`mxfp4_scaled_mm_<Suffix>_out_with_join_mode`（`TORCH_API`，无 Torch schema）。dispatcher 算子和原 `*_out` 入口固定使用 `SpawnJoin`，Torch 直调者不受影响。
  - commit `97a0f7c9eaebaf9c6e0052953cf79fc66536ac20`：[AsyncLaunch] use KernelJoinMode to basically support kernel launch with/without join
  - 测试：`torch_xcpu/test/mpi_custom_ops/test_fused_ep_moe_v5_mpi.py::check_trace`（只校验 shared MLP 与 dispatch 的 stream 任务顺序）。x86 上 `xthd_join` 为空操作，Spawn 语义没有可验证的测试。

- `silu_and_mul`（小修改）：`silu_and_mul_kernel` 与 `silu_and_mul_cpu_impl` 新增 `KernelJoinMode join_mode = SpawnJoin` 参数，A0 仅在 `SpawnJoin` 时执行 `xthd_join()`。
  - B0（目前是占位分支）实现时需要接受该参数并支持 `Spawn`。`silu_and_mul_cpu_impl_deferred_rows` 未改，Torch 入口行为不变。
  - commit `97a0f7c9eaebaf9c6e0052953cf79fc66536ac20`：[AsyncLaunch] use KernelJoinMode to basically support kernel launch with/without join
  - 测试：同上，仅有 stream 任务顺序校验。

### 不影响 B0 算子实现

- `fused_ep_moe_v5`（中等修改，host 编排）：两处变化。
  - SP padding：`topk_ids/topk_weights` 的行数从 `== hidden_states.size(0)` 放宽为 `<=`（C++ 校验与 FakeTensor 同步）。前 `topk_ids.size(0)` 行有效，`return_row_indices` 按 hidden 行数分配，`num_valid_rows` 传给 pack（已有参数）与 finalize；padding 行不分发、不跑融合 shared expert，输出为零。
  - 流式 launch：阻塞 dispatch 时，round 0 的 shared MLP（gate_up linear → `silu_and_mul` → down linear）改到 dispatch 之前，以 `KernelJoinMode::Spawn` 提交，与 alltoallv 重叠；设置 `TORCH_XCPU_FUSED_EP_MOE_V5_ASYNC_DISPATCH=1` 时仍在 `MPI_Ialltoallv` 之后以 `SpawnJoin` 提交。未量化 shared 权重经新增的 `torch_xcpu_addmm_v2_with_join_mode`，BLAS 不经 xthd，忽略 join_mode。
  - schema、workspace 公式与线协议未改。依赖的 B0 变化见上节 `moe_finalize_hybrid_reduce_v5_v8`、`fp8_linear`/`mxfp4_linear`、`silu_and_mul`。
  - commit `de3b6a151c3d0a4b6f605036278cd810cda9aa3b`：[MoE][SP] skip sequence-parallel padding rows in RMSNorm and fused EP MoE
  - commit `97a0f7c9eaebaf9c6e0052953cf79fc66536ac20`：[AsyncLaunch] use KernelJoinMode to basically support kernel launch with/without join
  - 测试：`torch_xcpu/test/mpi_custom_ops/test_fused_ep_moe_v5_mpi.py`（padding-row 用例与 trace 顺序断言）。

- `fused_ep_moe_v6`（小修改，host 编排）：同样把 `topk_ids` 行数放宽为 `<= hidden_states.size(0)`，把 `num_valid_rows` 传给 pack 和 finalize，`return_row_indices` 按 hidden 行数分配。kernel 契约变化见上节 `moe_prepare_hybrid_pack_v5_v8`、`moe_finalize_hybrid_reduce_v5_v8`。
  - commit `de3b6a151c3d0a4b6f605036278cd810cda9aa3b`：[MoE][SP] skip sequence-parallel padding rows in RMSNorm and fused EP MoE
  - 测试：未新增对应的专项测试。

- `sparse_attn_indexer`（小修改，C++ 组合编排）：与 vLLM 0.31 的 `needs_padded_path` 对齐，`requires_padding || num_decode_tokens % batch_size != 0` 时走 padded decode 路径。此前只看 metadata 标志，会把不规则 warmup/mixed batch（例如 3 个 decode token 分属 2 个请求）错误地按均匀方式 reshape。
  - 其他变化：topk buffer 跳过清零的条件同步增加整除要求；weights 必须连续 FP32 `[T,H]`（`stride(0)==H`，MQA logits kernel 不读行 stride）；decode `seq_lens` 至少一行；源码新增升级核对清单。
  - 只改变已有 `sparse_indexer_pack_seq`/`top_k_per_row_decode` 等算子的调用条件，各 kernel 的契约与 launch impl 未改。
