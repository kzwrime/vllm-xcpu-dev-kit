项目定位

Mooncake 是面向 LLM Serving 的、以 KVCache 为中心的解耦式架构。该项目是 Kimi 服务背后的 serving 平台之一，仓库中开源了 Transfer Engine、Mooncake Store，并包含技术报告与开源 trace。

Mooncake 的核心目标是把 prefill 集群和 decode 集群解耦，并利用 GPU 集群中相对未充分使用的 CPU、DRAM、SSD 等资源构建分布式 KVCache 池。其调度器以 KVCache 为中心，在满足延迟 SLO 的前提下最大化整体有效吞吐。README 中给出的实验结论包括：在长上下文场景中，Mooncake 相比 baseline 在部分模拟场景下可实现最高 525% 的吞吐提升；在真实工作负载下，该架构使 Kimi 能处理约 75% 更多请求。

Transfer Engine 能力

README 将 Transfer Engine 描述为高性能数据传输框架：它提供统一接口在 DRAM、VRAM、NVMe 等存储介质之间搬运数据，同时隐藏与硬件相关的细节。其支持的通信和传输协议包括 TCP、RDMA、AWS EFA、NVMe over Fabric、NVLink、HIP、Barex、CXL 以及 Ascend 系列传输路径。其中 RDMA 范围覆盖 InfiniBand、RoCEv2、eRDMA 和 NVIDIA GPUDirect RDMA。

能力说明
多 RDMA 网卡聚合支持同时使用多张 RDMA NIC，实现传输带宽聚合。
拓扑感知路径选择根据源端和目标端内存位置、NUMA 亲和性等信息选择更合适的设备。
临时网络错误恢复传输失败时可自动尝试替代路径，提升临时故障下的鲁棒性。
异构内存识别和路由在启用对应 runtime 时，可识别 CUDA、MUSA、HIP、MACA、Cambricon MLU、Ascend 等环境中的加速器内存。

性能数据

README 给出 Transfer Engine 的性能样例：以 40GB 数据为例，该数据量相当于 LLaMA3-70B 模型在 128k tokens 下产生的 KVCache 大小。在 4×200Gbps 和 8×400Gbps RoCE 网络中，Mooncake Transfer Engine 分别达到最高约 87GB/s 和 190GB/s 带宽，相比 TCP 协议约快 2.4 倍和 4.6 倍。

使用与构建要点

README 对使用路径的描述包括：CUDA 系统可安装 mooncake-transfer-engine 或 CUDA 13 对应包；非 CUDA 系统可安装 mooncake-transfer-engine-non-cuda。Docker 路径支持从源码构建 wheel 并安装，示例中强调 GPU/RDMA、host network、IPC、memlock、hugepage 等部署参数。源码构建需要 gcc/g++、cmake、Go；可选 CUDA、Neuware、DTK、CoreX、Rust、hiredis、curl 等依赖；标准流程是 mkdir build && cmake .. && make -j。

README 也指出 Mooncake 为高速 RDMA 网络设计和优化。虽然支持 TCP-only 数据传输，但进行功能和性能评估时建议使用 RDMA 网络。

1. 背景与动机

Mooncake Transfer Engine 把远端内存访问抽象成 Segment 和 BatchTransfer。网络后端只负责把统一 READ/WRITE 请求落到 TCP、RDMA、EFA、NVLink、CXL 等介质上。多后端设计同时覆盖标准 IP 网络可用性和生产网络高性能两个问题。

核心判断：新增定制网卡后端时，不应改应用层 API；应接入 Transport、MultiTransport、TransferMetadata 三个契约。

2. 核心抽象与路由机制

Mooncake 的网络后端设计分为三层：TransferEngineImpl 负责初始化 metadata/RPC 与安装策略，MultiTransport 负责后端工厂和请求路由，具体 Transport 负责真实数据面。这个分层让上层 Store/Python Binding 不直接感知 TCP、RDMA、EFA 或后续定制网卡的差异。

Transport 定义后端插件接口：安装、内存注册/注销、批量提交、状态查询。TransferTask 保存原始请求和 slice 列表；Slice 是后端实际提交的最小 I/O 单元。

3. TCP 后端

TCP 是最简单的可用后端，适合作为定制网卡后端的第一份模板。安装时分配数据端口，创建本地 segment，设置 protocol=tcp 和 tcp_data_port，启动 Asio accept 线程。内存注册不做硬件 pin，只把 addr/length 写入 metadata。

安装和元数据发布

TcpTransport::install() 做四件事：查找可用 TCP 数据端口；通过 allocateLocalSegmentID(tcp_port) 创建或更新本地 segment；启动 metadata handshake daemon；发布本地 segment 并启动 TcpTransport::worker() 线程。allocateLocalSegmentID() 会把协议写成 tcp，并把数据端口写入 tcp_data_port。

内存注册

TCP 没有真实 MR，也没有 rkey/lkey。registerLocalMemory() 只构造 BufferDesc，填入 name/addr/length，多协议模式下额外标注 buffer_desc.protocol = "tcp"，然后调用 metadata_->addLocalMemoryBuffer(...)。这说明 Mooncake 的“内存注册”不是必然等价于硬件 pin memory；对 TCP 来说，它更像是发布可远端访问的地址范围。

数据面

TCP 请求不分多片，每个 request 生成一个 slice：source_addr 指向本地 buffer，length 保存传输长度，opcode 保存 READ/WRITE，tcp.dest_addr 保存目标虚拟地址偏移，随后调用 startTransfer(slice)。

startTransfer() 读取目标 segment 与 RPC meta，连接目标 tcp_data_port，创建 ClientSession。会话头 SessionHeader 携带 size/addr/opcode；READ 表示服务端从目标地址读出数据并回传，WRITE 表示服务端接收客户端 body 并写入目标地址。完成后统一调用 slice->markSuccess()，失败调用 slice->markFailed()。

TCP 底层调用接口

TCP 后端底层不是直接调用 Linux send(2)/recv(2)，而是通过 standalone Asio 的 TCP socket API 封装异步 I/O。头文件 tcp_transport.h 引入 <asio/ip/tcp.hpp>，核心类型是 asio::ip::tcp::socket、asio::ip::tcp::acceptor 和 asio::io_context。

阶段底层接口说明
服务端建监听acceptor.open() / bind() / listen()优先 IPv6 dual-stack，失败后回退 IPv4
服务端接连接acceptor.async_accept(...)每个连接创建一个 ServerSession
客户端解析地址asio::ip::tcp::resolver::resolve()把目标 host/port 解析为 endpoint 列表
客户端建连asio::connect(*socket, endpoint_iterator)同步建立 TCP 连接；可选连接池复用
发送 headerasio::async_write(... asio::buffer(&header_ ...))header 包含目标地址、长度、READ/WRITE
发送 bodyasio::async_write(... asio::buffer(dram_buffer ...))WRITE 场景分块发送本地 buffer
接收 bodyasio::async_read(... asio::buffer(dram_buffer ...))READ 场景分块读回远端数据

如果编译时启用了 CUDA/MUSA/HIP/MLU/MACA 等宏，TCP 后端还会用 cudaPointerGetAttributes() 判断地址是否为设备内存；设备内存场景会用 cudaMemcpy(..., cudaMemcpyDefault) 在设备内存和临时 DRAM buffer 之间搬运，再交给 Asio socket。因此 TCP 后端在 GPU buffer 上不是零拷贝路径，而是“设备内存 staging + TCP socket”的兼容实现。

4. RDMA 后端

RDMA 是高性能后端模板，展示了 Mooncake 支持多网卡、拓扑选择、远端 key、连接池和失败重试的完整形态。它的复杂度主要来自两个事实：本地和远端内存都需要注册并暴露 key；一次用户请求可能被切分到多个网卡路径上并异步完成。

安装阶段

RdmaTransport::install() 要求传入 topology。它先调用 initializeRdmaResources()，遍历 topology 中的 HCA，为每张可用 RNIC 构造 RdmaContext；然后创建本地 segment、启动 handshake daemon、发布 segment。不可用设备会被禁用；如果没有可用 RNIC，安装失败。

内存注册

RDMA 注册会对每个 RdmaContext 调用 registerMemoryRegion()，收集每个 context 对应的 lkey/rkey，再根据 location 或地址自动识别 memory location，最终把 addr/length/name/lkey/rkey/protocol 写入 metadata。相比 TCP，RDMA 的 buffer metadata 是发起端能直接访问远端内存的必要凭证。

数据切片与设备选择

submitTransferTask() 会按 globalConfig().slice_size 切分请求。每个 slice 先在本地 segment 中选择 buffer/device，写入本地 source_lkey，再按 RdmaContext 聚合后提交给 worker pool。找不到已注册且 active 的本地设备时，会返回 AddressNotRegistered。

远端 rkey、endpoint 和完成队列

WorkerPool::submitPostSend() 再读取目标 segment，按目标地址选择远端 buffer/device，取出远端 rkey，构造 peer_nic_path，并按 shard 投递到 worker 队列。performPostSend() 获取或创建 endpoint；如果 endpoint 未连接，则主动发起 handshake；连接后调用 endpoint 的 post send 逻辑。最终 slice 会被转成 ibv_send_wr，设置 RDMA READ/WRITE、local lkey、remote addr、remote rkey，并调用 ibv_post_send()。

完成由 CQ polling 驱动：成功 work completion 调用 slice->markSuccess()；失败时删除 endpoint、增加 retry，并尝试 redispatch 到其他路径，超过重试次数后 markFailed()。

RDMA 设计点对定制网卡后端的启示
Context 表示本地网卡资源定制网卡也建议抽出 CustomContext 管 device/queue/key
Endpoint 表示本地网卡到远端网卡连接如果网卡需要 QP/session/channel，也抽 CustomEndpoint
metadata 暴露远端 key定制后端必须定义可序列化的 remote access token
worker pool 解耦提交和完成有异步 completion queue 时应照 RDMA 做
retry/redispatch 与 topology 绑定多网卡场景要定义失败后的替代路径选择

5. 新增定制网卡后端的最小路径

假设新协议名为 customnic。新增后端的目标不是把数据发送逻辑塞进现有 RDMA/TCP，而是让它作为独立 Transport 接入工厂、metadata、任务提交和完成状态四个契约。

最小文件结构

mooncake-transfer-engine/include/transport/customnic_transport/customnic_transport.h
mooncake-transfer-engine/src/transport/customnic_transport/customnic_transport.cpp
mooncake-transfer-engine/src/transport/customnic_transport/CMakeLists.txt

如果网卡有异步队列，建议继续拆出 customnic_context、customnic_endpoint、customnic_worker_pool，避免一个 transport 文件同时承担设备、连接、提交和完成逻辑。

接入编译和工厂

  1. 在顶层 CMake 增加 USE_CUSTOMNIC 选项。
  2. 在 transport 子目录 CMake 中纳入 customnic_transport object library。
  3. 在 multi_transport.cpp include 头文件，并在 installTransport() 加入 proto == "customnic" 分支。
  4. 实现继承 Transport 的 CustomNicTransport。
#ifdef USE_CUSTOMNIC
else if (std::string(proto) == "customnic") {
    transport = new CustomNicTransport();
}
#endif

推荐实现顺序

  1. 骨架后端：继承 Transport，实现 install/register/unregister/submit/status。
  2. 单连接、单 slice：先不切片、不多网卡，像 TCP 一样每个 request 一个 slice。
  3. 完成语义打通：底层回调或 polling 完成后只做两件事：slice->markSuccess() 或 slice->markFailed()。
  4. remote key 支持：注册内存时写入定制 key，发起端从目标 segment 读取 key。
  5. 多网卡与 topology：引入 CustomContext，按 location 选择本地/远端 device。
  6. 重试和失败隔离：参考 RDMA worker pool，失败时换 endpoint/device。
class CustomNicTransport : public Transport {
  int install(...) override;
  int registerLocalMemory(...) override;
  int unregisterLocalMemory(...) override;
  Status submitTransferTask(const std::vector<TransferTask*>&) override;
  Status getTransferStatus(BatchID, size_t, TransferStatus&) override;
};
